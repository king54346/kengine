# benches

```bash
cargo bench                          # 全部
cargo bench --bench physics          # 一组
cargo bench -- 'culling'             # 按名字过滤（正则）
cargo bench -- --save-baseline main  # 存一个基线
cargo bench -- --baseline main       # 跟它比
```

HTML 报告在 `target/criterion/report/index.html`。

## 覆盖了什么

| 文件 | 内容 |
|---|---|
| `scene.rs` | `Scene::update`（平铺 / 深链）、视锥剔除（部分可见 / 全可见） |
| `physics.rs` | 步进（自由落体 / 堆叠 / 关节链）、射线（打中 / 打空） |
| `rendering_paths.rs` | 粒子推进与收集、蒙皮、调试线生成 |
| `serialization.rs` | 场景存盘、读盘、存盘体积 |
| `script.rs` | 一次 tick 的固定开销、脚本节点扫描、空回调、包装层 vs 裸桥 |

## 没覆盖什么

**批处理与绘制提交量不了。** 那部分在 `Renderer::render` 里，需要一个 wgpu
设备，headless 起不来。它仍然只能靠 demo 里的 `prepare_micros` 观察。
这是已知盲区，不假装覆盖了。

## ⚠️ 关于这些数字能信到什么程度

**开发机上的绝对数字不可信，criterion 的 `change:` 百分比同样不可信。**

实测：同一条 bench、同样的代码、隔一分钟连跑三次——

```
gizmos/sphere/1000    225 µs  →  581 µs  →  510 µs
gizmos/aabb/10000     519 µs  → 1359 µs  →  613 µs
```

**差到 2.6 倍。** criterion 能把单次测量的置信区间收窄到 ±5%，但它对
「两次运行之间整台机器变慢了」无能为力——它只会如实报告「性能下降了 140%」。

这不是 criterion 的缺陷，是它的适用前提：**基线和对比必须在同样的机器状态下取。**

### 于是有两条规矩

**一、CI 只编不跑。** `cargo bench --no-run`。CI runner 的性能波动比本机还大，
跑出来的数字没有比较意义；但 bench 代码会随 API 变动而失效，编不过要立刻知道。

**二、要下性能结论，同一轮里必须有一条不变的对照。**

> `script.rs` 是照这条规矩设计的：`control/scene_update` 完全不碰脚本系统，
> 同一轮里它涨了多少，机器就慢了多少；`raw_bridge` 与 `running` 做的是同一件事、
> 只差一层包装，两者的差值不受机器状态影响。


举个刚发生的例子。给 `Gizmos::ring` 加单位圆查表之后：

- criterion 报 `sphere/1000` **-88.5%**（p = 0.00）——看着像 9 倍提速；
- 但同一轮里**代码根本没动**的 `aabb/10000` 也报了 **-53%**。

后者就是对照：它说明这一轮机器本身快了一倍多。真正能站住的说法是
**同一轮内的每顶点相对开销**——它把机器状态约掉了：

| | 球（每顶点） | 盒（每顶点） | 比值 |
|---|---:|---:|---:|
| 查表前 | 14.6 ns | 4.5 ns | **3.24** |
| 查表后 | 1.56 ns | 2.16 ns | **0.72** |

球从「比盒贵 3.2 倍」变成「比盒还便宜」。这个结论跟机器多快无关，
所以它才是能写进文档的那一个。（后续几轮量到的比值在 0.7~1.4 之间浮动，
即使取最保守的 1.4，也仍是两倍以上的改善。）

### 想要可信的绝对数字，就得

- 关掉别的程序，尤其是浏览器和 IDE 的后台索引；
- 关掉 CPU 睿频 / 省电调频（笔记本插电，Windows 电源计划设「高性能」）；
- 同一轮内先 `--save-baseline`，改完立刻 `--baseline` 对比，中间别做别的事；
- **永远留一条不受改动影响的 bench 当对照。**

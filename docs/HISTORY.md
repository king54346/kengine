### 二、三个必须先解决的架构冲突

a.md 的部分描述来自 Bevy 的 ECS 架构，而项目已确定走 **Fyrox 式场景图**路线。以下三处需要重新定义，否则动工即返工。

#### 1. `ktask` 的定位

- **a.md 原文**：「每个『就绪』System 被包装成 async task 丢进线程池……完成通道通知调度器，触发下游依赖的 System 就绪」
- **冲突**：这是 ECS 的 System 依赖图并行调度，前提是有 ECS 存储与 Query 冲突分析
- **改为**：定位为**并行计算与 IO 池**——资源异步加载（已在用）、批量变换计算、剔除并行化、网格处理。不做 System 调度器

#### 2. `kapp` 的 Schedule

- **a.md 原文**：「App、Plugin、Schedule 阶段」
- **改为**：**固定阶段的更新循环**，而非可插拔的 System 依赖图：
  ```
  Input → Update → PostUpdate → ┬─ FixedUpdate → 物理步进 → Physics ─┬→ Transform → Culling → Render → FrameEnd
                                └────────── 每子步重复 0~N 次 ───────┘
  ```
  插件在指定阶段注册回调。这保留了 a.md 的分阶段意图，又不需要 ECS。

#### 3. `krender` 的 RenderGraph

- **a.md 原文**：「RenderApp、RenderGraph、提取/准备/队列的渲染阶段」
- **冲突**：extract 阶段的意义是把数据从 ECS World 拷到独立的 RenderWorld 以便并行；场景图架构下没有这个必要
- **改为**：**固定管线阶段** `收集 → 剔除 → 排序 → 批处理 → 提交`。RenderGraph（多 pass 编排）留到需要阴影/后处理时再引入，那时它是真需求

- [x] **粒子特效** ✅ — 新增 `kparticle`（2078 行含测试与着色器，63 项测试）
      + krender 的粒子 pass（473 行）。全量测试 396 → 473。

      **存储用列而不是行**：粒子不是 `Vec<Particle>`，而是每个属性各占一个数组（SoA）——
      这是 Bevy 的 ECS `Table` 的做法（*列式连续内存，为快速迭代优化*）。
      死亡粒子用 `swap_remove` 就地填补，池子永远紧凑，迭代不需要判断「这个还活着吗」。
      超过 2048 个粒子时按列切片分给 ktask 并行推进，与串行结果逐位一致（有测试锁定）。

      **没有引入全局 ECS `World`**：引擎已是场景图架构（见第二节），
      为一个子系统再引入一套实体存储只会多出一层要同步的状态。
      ECS 在这里有价值的是**存储布局**，不是调度器。

      **语义照 Fyrox**：发射器形状（点/球/盒/圆盘）+ 方向与发散角、
      按速率累积生成（不足一个的零头留到下一帧，否则低速率下永远出不来粒子）、
      颜色与大小随归一化寿命走关键帧曲线、局部/世界两种演化空间。
      随机数是自带的确定性 PCG32，同种子必然重放同一段演出——粒子因此可以回归测试。

      **渲染**：方片在顶点着色器里长出来（CPU 每帧只传一个粒子数组，不重建顶点缓冲），
      沿相机的右/上向量张开以正对镜头；画在不透明物体与天空**之后**，
      只测深度不写深度，按到相机的距离从远到近排序（alpha 混合不可交换，顺序即正确性）。
      片元输出预乘 alpha，于是「半透明」与「相加」两种混合共用一个片元着色器、只差混合状态。

      **未做**：软粒子（与场景深度相交处淡出，需要可采样的深度纹理）、
      GPU 端模拟（计算着色器）、拖尾/网格粒子。
      **粒子碰撞**当时也在这一栏，**已在阶段 4 之后补上**（见下面「粒子碰撞」一节）——
      当时做不了是因为还没有物理世界可撞。

- [x] **顺带修掉的性能问题** ✅ — `Scene` 新增按组件分类的节点句柄索引，
      由 `update` 沿树遍历时顺手收集。

      起因是粒子接进来后万级场景掉到 51 FPS，而**剔除耗时也翻了一倍**——
      粒子根本不参与剔除，这只能是缓存被冲掉了：新加的 `tick_particles` 与
      `visible_particles` 每帧把两万个 `Node`（约 6 MB）整个扫一遍找那两个粒子节点，
      顺带把紧随其后的剔除要用的数据挤出了缓存。
      查下去发现 `visible_lights` / `active_camera` / `shadow_caster` 早就是这么写的，
      于是一并改成走索引。改完帧率回到 58–59 FPS，与没有粒子时在噪声内无差异。

**验收**：PBR 参数网格在 IBL 下呈现正确的环境反射；多光源场景帧率可接受。
demo 里有两组粒子（相加混合的火花、半透明烟雾），按 F 手动喷发一团。

实测（release）：254 个粒子只多花 2 次绘制调用；
普通场景剔除 10 µs、CPU 准备 90 µs；
万级场景下开/关粒子的相邻 A/B 均为 58 FPS、剔除 ~360 µs、CPU 准备 ~2.5 ms，
差异落在机器噪声内。

**踩到的坑**：WGSL 里 `vec3` 的对齐是 16 字节，写在结构体末尾的 `vec3` 填充
会把自己推到偏移 48，整个结构体从 48 涨到 64，与 CPU 侧紧凑排布对不上，
绑定时被 wgpu 打回。现在由 `kparticle` 的测试用 naga 按 WGSL 规则算一遍布局、
与 Rust 结构体对拍来兜住——比人工数字节可靠。

**风险**：IBL 的 G 项必须用 `k=α/2` 而非直接光照的 `k=(r+1)²/8`，混用会导致亮度偏差——已在 `pbr.wgsl` 注释标注。

#### 阶段 2：场景与性能 ✅ 已完成

- [x] **空间划分** ✅ — `kmath::Bvh`，分箱 SAH 构建 + refit。
      选 BVH 而非八叉树：八叉树按空间均匀切分，物体尺寸悬殊时（大地面 + 小石头）会大量跨格。
      场景侧策略：节点增删或可见性变化 → 重建；只是变换变了 → refit（O(n)，不改树形）；
      什么都没动 → 整棵复用。大场景连续 refit 240 帧后强制重建，避免树形随物体移动持续退化。
      查询用**三态**判定（`Intersection::Outside/Intersects/Inside`）：
      子树整个在视锥内就一次收下，不再逐个判定。
- [x] **剔除并行化** ✅ — 对象数超过 4096 时，把 BVH 切成 `线程数 × 4` 棵子树，
      用 ktask 分片并行遍历。「整棵树的深度优先」等于「有序切分后各子树深度优先的拼接」，
      因此并行结果与串行**逐字节一致**，绘制顺序不随线程调度抖动（有测试锁定）。
      kscene 因此打开了 ktask 的 `multi_threaded` feature。
- [x] **绘制批处理** ✅ — 按 (网格, 五张贴图的组合) 排序后切分批次。
      排序的是下标而非绘制项本身——`DrawCall` 有两百多字节，上万对象直接排序光搬运就很贵。
      材质的**数值**参数（颜色、金属度……）不参与分批，它们是逐实例数据。
- [x] **实例化渲染** ✅ — 每对象 uniform 从「uniform + 动态偏移」改为**存储缓冲 + `instance_index`**。
      前者每个对象都要重绑一次绑定组，也就注定一个对象一次 draw；后者让着色器自己按实例号取数，
      一批合并成一次 `draw_indexed`。片元着色器通过 `@interpolate(flat)` 的实例号取材质参数。
      阴影深度 pass 同样改造，并沿用主 pass 的分批以保证两边实例下标一一对应。

**验收结果**（release，20067 个对象，其中 4313 个可见）：

| 指标 | 数值 |
|---|---|
| 剔除耗时 | **0.3–0.5 ms/帧**（线性剔除同机相邻测量为 0.9–1.1 ms，约 2.2 倍） |
| CPU 准备总耗时 | 2.4–3.9 ms/帧（剔除占 ~13%） |
| 绘制调用 | **8 次**画完 4313 个实例（平均 539 个/次） |
| 帧率 | 58–59 FPS（垂直同步封顶 60） |

原 demo 场景的渲染统计与阶段 1 逐字节一致（36 绘制 / 31 剔除 / 28882 三角形），
绘制调用则从 36 降到 7。复现：`cargo run --release -- --stress 20000`，按 C 打印统计。

**测量说明**：这台机器的耗时波动可达 ±40%（频率调节 / 后台负载），
上表给的是区间而非单点，BVH 与线性的对比取的是相邻两次运行。

**下一个瓶颈**：CPU 准备里约 2 ms 花在收集循环上（每个可见对象 ~470 ns），
主要是材质参数的字符串键查表——`Material` 用 `FxHashMap<String, _>` 存参数，
每个对象要查 8 次。想进一步优化得先给材质一个可靠的内容版本号（目前 `set` 不改 `id`，
克隆后修改会得到 id 相同内容不同的两份材质，没法安全缓存）。这属于资源层的改动，留给阶段 3
——**已在阶段 3 解决**，`Material` 现在带内容版本号，缓存键是 `(id, version)`。

- [x] **网格共享（地基）** ✅ —— `Mesh` 内部改成 `Arc<MeshData>`，克隆从深拷贝变成 O(1)。

      起因是序列化：`Node.mesh` 是**按值**持有的，`--stress 20000` 那片方块
      在内存里躺着两万份立方体顶点，存盘还会把几何抄两万遍。
      改成写时复制之后，「共享」对调用方完全透明。

      **改内容就换新 `id`**：几何被 `Arc` 共享着，改完之后这份 `Mesh` 已经和
      其它副本不同了，再共用一个显存缓存键就会画出别人的顶点。
      **改内容还会作废「出处」**——不作废的话，场景会存成一行资源引用，
      读回来却是未经修改的原始几何。这两条都有测试锁定。

      `Mesh` 同时增加了**出处**（`MeshSource { path, index }`），由 glTF 导入器打上。

- [x] **材质内容版本号** ✅（阶段 2 遗留）—— 阶段 2 记的原话是「`set` 不改 `id`，
      克隆后修改会得到 id 相同内容不同的两份材质，没法安全缓存」。
      现在 `Material` 带一个 `version`，每次改动 +1，缓存键是 `(id, version)`。

      用版本号而不是「改动就换新 id」：换 id 会让渲染器把管线、绑定组连同贴图
      一起重建，而绝大多数改动（调个颜色、改个粗糙度）只影响那一小块逐实例参数。

- [x] **场景序列化** ✅ —— `Scene::save` / `load` / `save_text`，格式带版本号，
      读到不认识的版本直接报错而不是按老规则硬解释。

      **网格与材质各走一张共享表**，按 id / 内容缓存键去重。一片一万个方块的
      场景里那一万个节点共用同一份几何：逐节点内联的话文件会涨到几百 MB，
      读回来还会得到一万份互不相干的副本，显存缓存与批处理全部失效。
      有测试直接量「多一个共享节点」与「多一个自带几何的节点」各要多少字节。

      **能引用就不内联**：从 glTF 导入的网格表里只写一行「`Soldier.glb` 的第 3 个
      网格」，读回来重新请求那个模型；程序化生成的网格没有出处，只能内联。
      模型文件被挪走时**不让整个存档读不进来**——记一条日志，那个节点不带网格。

      **资源引用一律存路径**，读取端从 Visitor 的 **blackboard** 里取
      `ResourceManager` 重新请求（这正是 blackboard 存在的理由）。
      拿不到管理器时**明确报错**，而不是悄悄给个空资源、等到渲染时才发现贴图全丢了。

      配套补齐了一批 `Visit`：glam 的 `Vec2/3/4`、`Quat`、`Mat3/4`（孤儿规则要求
      写在拥有 `Visit` 的 kcore 里，而不是 kmath）、`Aabb`/`Plane`、`Sky`/`Environment`、
      `Light`/`Camera`、`Mesh`/`Material`、物理的各种描述结构。
      **枚举的类型标签一律显式写死**：靠声明顺序的话，将来在中间插一个变体，
      老文件里的点光源会被读成聚光灯，而且不报错。
      **派生数据一概不存**（包围盒、球谐系数、骨骼矩阵、形变增量范围），
      读回来重算——存一份派生数据就多一处可能和本体对不上的「真相」。

      **未纳入序列化**：粒子系统、动画播放器、布娃娃。它们要么是纯运行时状态，
      要么依赖资源里的数据。存盘时会在日志里说清楚跳过了几个，不搞悄悄丢失。

- [x] **资源打包** ✅ —— `PackWriter` / `PackResourceIo`，格式 `KPAK`。
      加载器一行代码都不用改，这正是当初把 `ResourceIo` 抽出来的原因。

      目录放在文件**前面**：读包只需顺序读一小段就能建好索引，不必先跳到末尾——
      将来接网络流式读取时这一点会变得重要。
      目录按路径排序，同一批文件必然打出同样的字节，增量发布能靠比对哈希判断。
      路径分隔符统一成 `/`：不统一的话同一个包换台机器就读不出来。
      **坏包在打开时就报错**（越界、截断、版本不符），而不是等某个资源被请求时才炸。

      另有 `LayeredResourceIo`：散文件优先、包兜底。开发时改个贴图往
      `assets/` 一放就生效，发布时目录不存在自动落到包上。

> **补记：一个偶发的漏收 bug ★**
> `collect_unused` 的判据是「引用计数 > 1 就说明还有人在用」，
> 但加载任务在 `commit` 之后仍短暂持有一份强引用，而 `commit` **内部**
> 就已经唤醒了等待者——于是 `request_blocking` 返回那一刻计数还是 2，
> **刚加载完的资源回收不掉**。
>
> 这个窗口只在 IO 池忙不过来时才张开，所以单独跑必过、全工作区并行跑时偶发，
> 属于最难查的一类。人为把 IO 池占满之后稳定复现：两百次里八十四次漏收。
> 修法是让 `commit` 按值拿走句柄，**唤醒之前先松手**。
> 同样的压力条件下现在 200/200 全部回收成功，已固化成回归测试。

- [x] **热重载** ✅ —— `HotReload` 按修改时间轮询，`App::with_hot_reload` 开关，
      排在帧末（这一帧的逻辑与渲染已经用完旧数据，换在这里最不容易撞上
      「用到一半资源被换掉」）。

      **数据就地替换**：`ResourceManager::reload` 把新数据写回同一个资源头，
      所有已存在的句柄立刻看到新内容，不需要通知任何人、也不需要重建场景。
      这是热重载能成立的前提。

      **轮询而不是文件系统事件**：`notify` 那类库更即时，代价是一个不小的依赖、
      一个后台线程，以及各平台事件语义的差异（一次保存在不同编辑器下可能触发
      1 到 4 个事件）。只看已请求过的那几十上百个资源、每秒查一次 `mtime`，
      换来零依赖、跨平台一致、测试里能精确控制时序。
      **删文件不触发重载**——那只会把好好的资源变成加载失败。

- [x] **流式加载** ✅ —— `Streaming` + `Cell`，形态是**显式分区 + 距离激活**。

      为什么不是「引擎按网格自动切分」：自动切分需要知道什么东西该跟什么东西
      一起加载（一栋楼和它的门、一个房间和它的灯），而这个信息只有做关卡的人有。
      显式分区把决定权留在它该在的地方，「按距离自动装卸」的便利一点没少；
      两个距离设成无穷大就退化成完全手动。

      **迟滞是必须的**：加载距离必须小于卸载距离，相等的话观察者站在边界上
      会每帧装一次卸一次，帧率直接归零——这是流式加载最经典的翻车方式，
      所以 `with_distances` 会强制把两者拉开 10%，有测试站在边界上反复 update 来验。

      **装载有预算**：一次 `update` 最多装 N 个。玩家瞬移到地图另一头时，
      没有预算就要在一帧里读进几十个区块，表现为数秒卡死。宁可远处的晚几帧出现。
      候选按距离排序，先装最近的。
      **加载失败不重试**：文件缺失或格式不对，重试一万次也不会自己好，
      只会每帧刷一屏日志；想再试得显式调 `force_load`。

      底层原语是新增的 `Scene::merge`——把一个场景整个并进另一个。
      **每一处存着节点句柄的地方都要重映射**：父子关系、骨架的关节表、
      关节组件两端的刚体。漏掉任何一处，症状都是「并进来之后有几个节点
      莫名其妙地跟着另一个物体动」，而且不报错。三处各有一个测试。

- [x] **ksprite** ✅ —— 精灵 / 图集 / 帧动画（一次性、循环、来回播）。

      **不自带渲染管线**。一个精灵最终就是一张贴了图的方片，而引擎已经有
      一条画「网格 + 材质」的路径了。所以 ksprite 产出的是方片网格加一对
      UV 变换参数，交给现成的管线画——于是精灵天然享有已有的批处理、实例化、
      剔除、光照与后处理，渲染器只多了一对标准材质参数 `uv_scale` / `uv_offset`
      （`ObjectUniforms` 相应从 192 涨到 208 字节）。
      代价是走 3D 管线，逐精灵开销比专用 2D 批处理器高；真要画几万个再补不迟。

      **方片的 UV 恒为 0..1**，取哪一格全在那两个数值参数里。换帧只改两个数，
      不必重建顶点缓冲，同一张图集上的所有精灵还能共用一份网格合批。

      **来回播的两端各只出现一次**（`0,1,2,3,2,1`）：两端各显示两次的话，
      看起来像每到头就卡一拍。

- [x] **kutils** ✅（按原计划：什么都不建）—— 这一阶段沉淀出的通用件都各自
      找到了本来就该在的家：资源引用的序列化进了 kasset，glam 的 `Visit`
      按孤儿规则只能进 kcore，可选组件的读写助手留在 kscene。
      没有任何东西重复到需要单开一个 crate。计划里写的就是「按实际需要沉淀，
      不预先设计」，那么诚实的结论就是**现在还不需要**。

**验收结果**：`cargo run --release -- --roundtrip` 会自动跑一遍
「跑 3 秒 → 存盘 → 读档 → 对比渲染统计」，因为「画面完全一致」没法靠肉眼确认，
按键又没法在无头环境里按：

```
存盘前：63 绘制 / 49544 三角形 / 22 绘制调用 / 266 粒子
读档后：63 绘制 / 49544 三角形 / 20 绘制调用 /   0 粒子
```

几何逐项一致。绘制调用少的 2 次正是两个粒子 pass，粒子归零是预期的
（不在存档范围内）。整个 demo 场景 341 KB。
demo 里另加了三个精灵（静止 / 循环 / 来回播），它们和别的网格一样存得下、读得回。
`--pack` 会把 `assets/` 打成资源包并从包里读，与 `--roundtrip` 叠加后结论不变。
交互上是 F5 存盘、F9 读档。

**踩到的坑**：读档时用 `set_mesh` 把网格接回节点，它会把形变权重重置成网格自带的
默认值，于是狮子的表情在存读之后全归零。改成直接赋值 + 按目标数补齐。
另一个是 demo 侧的：读档后把 `*_spawned` 标记复位，导致模型又被实例化了一遍，
几何整整多出一份（+19352 三角形，正好是士兵加狮子）。两个都是自检对比抓出来的。

- [x] **选型确认** ✅ —— **改用 Rapier，放弃 Jolt**。

      Jolt 是 C++ 库，Rust 侧要经 FFI；`jolt-rust` / `joltc-sys` 覆盖不全、
      绑定层要自己补，还会给整个工作区引入 cmake + C++ 工具链与跨平台链接配置。
      本项目从 kcore 到 kparticle 全是纯 Rust、`cargo test` 一条命令跑完，
      这个性质不值得为物理放弃。Rapier 是纯 Rust，且 **Fyrox 用的就是它**
      （`scene/graph/physics/`，4006 行），参考实现可以逐行对照。

      **意外收获**：Rapier 0.35 起公开的数学类型已从 nalgebra 换成 **glam**
      （`pub type Vector = Vec3`、`Rotation = Quat`），与本项目同源。
      Fyrox 用的 0.33 还是 nalgebra，那一层厚重的转换代码这里完全不需要。
      唯一的落差是版本：rapier 锁 glam 0.33，kmath 用 0.29，同名不同版在 Rust 里
      是两个类型，仍要转一道——但只是 `Vec3::new(v.x, v.y, v.z)` 级别，优化后不留痕迹。
      没有为此升级 kmath：0.29 → 0.33 会波及 kmesh / kcamera / krender / kanim 全线，
      收益却只是省掉几十行搬运代码。

- [x] **刚体动力学 / 碰撞检测 / 碰撞响应** ✅ —— 四种刚体类型（动态 / 静态 /
      运动学位置驱动 / 运动学速度驱动）、九种碰撞体形状（球 / 盒 / 胶囊 / 圆柱 /
      圆锥 / 半空间 / 三角网格 / 凸包 / 高度场 / 复合）、摩擦与弹性及其合成规则、
      碰撞分组、传感器与碰撞事件、休眠、CCD、锁轴、支配组。

      **`kphysics` 是全项目唯一依赖 rapier 的 crate**，作用与 krender 之于 wgpu 相同：
      对外只暴露 kmath 的 `Vec3`/`Quat` 与自己的不透明句柄，rapier 的类型一个都不外泄。
      刚体上的 `user_data`（一个 `u128`）是留给上层的唯一的洞，`kscene` 往里塞节点句柄。

      **退化几何返回 `Option` 而不是 panic**：凸包点共面、三角网格为空、
      高度场尺寸对不上，都只能在构建时才发现。一个坏模型不该让整个游戏挂掉。

- [x] **射线检测** ✅ —— 射线（最近命中 / 全部命中按距离排序）、形状扫掠、
      点投影、点/形状重叠查询，都支持分组过滤与排除指定刚体。
      `Scene::cast_ray` 在此之上把 `user_data` 解回**节点句柄**，
      这正是那个 `u128` 被塞进去的用途。

- [x] **布娃娃** ✅ —— `RagdollBuilder` 按肢体描述树搭出刚体 + 碰撞体 + 关节。
      关节锚点自动算：关节点就是子骨骼的原点，在子刚体局部空间里是原点本身，
      在父刚体局部空间里换算一次即可。用户只需要挑关节类型与限位——那才是要调的部分。

      **两个方向，切换时不能穿帮**（语义取自 Fyrox 的 `ragdoll.rs`）：
      未激活时刚体切成运动学、**每帧被摆到骨骼所在的位置**；激活时切回动态、
      模拟结果写进骨骼的局部变换。未激活时也老老实实跟着骨骼摆，是为了激活那一刻
      刚体不会停在几秒前的位置、角色从那里「闪现」过来。
      刚激活的一帧还会把角色本体的速度分给各肢体，否则奔跑中的角色会原地软倒。

      **肢体刚体与骨骼树是两棵独立的树**：混在一起的话，激活时骨骼的局部变换正被
      物理改写，而刚体的世界位姿又依赖骨骼的世界变换，两者会互相追着跑。

- [x] **物理与场景图的变换同步** ✅ —— `RigidBody` / `Collider` / `Joint` 是挂在
      `Node` 上的组件（全部装箱，理由与粒子相同：绝大多数节点没有物理，
      内联会让每个 `Node` 白背上百字节）。

      **谁驱动谁**是整套逻辑里唯一要记住的事，方向搞反症状极其费解：

      | 组件 | 方向 |
      |---|---|
      | 动态刚体 | 物理 → 场景图，每帧写回节点局部变换 |
      | 静态 / 运动学刚体 | 场景图 → 物理，改节点变换就是在驱动它们 |
      | 无刚体的碰撞体 | 场景图 → 物理 |

      因此**动态刚体不能靠改 `node.transform` 移动**——下一次同步就被覆盖了。
      要瞬移用 `teleport`，要推它用 `apply_impulse`。这与 Fyrox 的语义一致，
      并有测试专门锁住这个「反直觉但正确」的行为。

      **碰撞体绑定到自己或最近的带刚体的祖先**，一个都没有就是静态几何。
      于是简单物体可以把刚体和碰撞体挂同一个节点，复合物体给刚体节点挂若干个
      带偏移的碰撞体子节点，两种写法都成立。

      **操作走队列**：用户在 `update` 里调 `apply_impulse` 时，原生刚体可能还没建出来
      （节点是这一帧刚加的）。排进队列、到同步那一刻统一执行，调用方就不必关心时序
      （Fyrox 的 `RigidBody::actions` 同思路）。属性改动则用一个脏标记整体重推——
      物理节点通常只有几十个，逐字段追踪的复杂度不划算。

      **同步用的是沿父链实时算的世界变换**，而不是 `node.global_transform()`：
      后者是上一次 `update` 的结果，而物理排在 `update` 之前，这一帧新加的节点、
      刚被逻辑改过的变换在那里都还没体现。代价 O(树深)，物理节点很少，可以忽略。

- [x] **固定步长** ✅ —— `kapp::PhysicsClock`。物理必须用定长步长：变长步长下
      同一个场景每次跑出的结果都不一样，帧率一抖堆叠的箱子就会莫名其妙地塌。
      累加器把真实帧间隔切成定长子步，零头留到下一帧。
      单帧最多 4 步、单帧最多接受 0.25 秒——上限是为了避免**死亡螺旋**：
      某帧卡了 2 秒，不限制的话这一帧要补 120 步物理，于是卡得更久，于是要补更多步。
      宁可让物理相对现实时间变慢，也不能让它把自己拖死。

      > **补记（阶段 7 之后）**：当时只做了「物理模拟定长」，**没做用户逻辑的定长入口**——
      > `Stage::Physics` 每帧只跑一次、在所有子步之后。已补上 `Stage::FixedUpdate`
      > 与 `Plugin::fixed_update`，并把 `Stage::Physics` 改成跟着子步跑。
      > 详见「补：Fixed Update 调度」一节。

**一帧的顺序**（`Stage` 新增 `Physics`，排在 `PostUpdate` 与 `Transform` 之间）：

```
插件 update/post_update → tick_animations（动画写局部变换）
   → step_physics ×N（布娃娃跟骨骼 → 同步到物理 → 步进 → 写回局部变换 → 布娃娃驱动骨骼）
   → update（世界变换 → 骨骼矩阵 → 包围盒）→ tick_particles → 剔除 → 渲染
```

物理排在动画之后：未激活的布娃娃要跟着这一帧的动画姿态走。
排在 `update` 之前：物理写的也是局部变换，世界变换要在之后统一重算——
这样全帧只有一趟 `update`，包围盒与剔除结构自然带上物理的结果。

**踩到的坑 ★**：查询走的是广相 BVH，而 BVH 是在 `step` 里维护的。
刚建好世界还没步进过就打射线，会**静默返回空结果**——不报错、不 panic，
只是什么都查不到，是最难查的那种问题。现在增删刚体/碰撞体会置脏标记，
并提供 `update_query_structures()` 显式刷新（内部是一步 `dt = 0` 的空步进，
Fyrox 冻结物理时用的也是这一手）。这个行为连同它的解药一起有测试钉住。

**验收结果**：demo 里加了一片物理场地（+X 一侧）——码成金字塔的 15 个箱子、
一个铰链单摆、一部运动学电梯、一个传感器触发区。
按 P 从相机打射线拾取并施加冲量、同时发射一颗开了 CCD 的炮弹，
X 重码箱子，G 开关重力，K 切换士兵布娃娃（12 节肢体的 Mixamo 人形）。

##### 补：粒子碰撞 ✅

阶段 1 把「粒子碰撞」记在未做栏里，理由是那时没有物理世界可撞。物理就位之后补上，
新增 35 项测试（kparticle 32 / kscene 3）。

**分两级，因为代价差了三个数量级：**

| | 做法 | 代价 | 适用 |
|---|---|---|---|
| 平面碰撞 | 一组无限大平面，逐粒子一次点积 | 可忽略 | 地面、四壁、桌面——绝大多数需求 |
| 场景碰撞 | 对物理世界打射线 | 很贵 | 要真的从箱子上弹起来时 |

场景碰撞**按预算轮转**：逐粒子每帧一次射线，四千个粒子就是每秒二十四万次查询，
足以吃掉整个帧预算。所以每帧只查一小批（默认 64 个），游标接着上次往下走。
代价是一颗粒子平均每 `粒子数 / 预算` 帧才被检测一次，表现为个别粒子晚几帧才弹起来——
视觉上察觉不到，而每帧全量检测的卡顿一眼就能看出来。这也是 Unity / Unreal 的通行做法。

**分层没破**：kparticle 仍然不依赖物理引擎。平面碰撞是纯数学；场景碰撞由调用方传一个
射线检测闭包进来，kscene 用 kphysics 填上这个洞。于是 kparticle 照旧能在没有物理、
没有 GPU 的环境里完整测试。

**粒子是只受影响、不施加影响的一方**：碰撞只做查询，一个字节的刚体状态都不改——
一场火花不该把箱子掀翻。有测试拿 256 颗粒子砸一个箱子来验。

**线段是精确的，不是近似**：半隐式欧拉下 `p_old = p_new - v_new·dt` 严格成立，
所以射线检测拿到的就是粒子这一帧真正走过的那一段。

**记了一个「看起来像 bug 其实不是」的测试**：出生就贴着地面的粒子每帧会被重力
拉进去一点点、再被推回来，幅度是亚毫米级。这是离散碰撞的正常表现，
单独写了一个测试把幅度钉在 0.01 以内，免得下次有人以为它坏了。

demo 里按 F 喷出的火花会从地面和箱子上弹起来，每次弹跳折掉三成寿命，弹几下就熄灭；
烟雾只配了一块地面平面——为它做逐粒子射线检测是纯浪费。加上碰撞后帧率仍是 59 FPS。

**未做**：粒子之间的碰撞（要空间划分，而粒子互撞在视觉上几乎没有收益）、
粒子对刚体施加反作用力。

##### 补：Fixed Update 调度 ✅

阶段 4 声称「固定步长」，实际只做了一半：**物理模拟**是定长的，但**用户逻辑没有定长入口**。
`Stage::Physics` 的系统每帧只跑一次、在所有子步之后，`Plugin` 也没有 `fixed_update`。

**这不是纸面缺陷，它导致了一个真 bug**：`PhysicsWorld::step` 每次开头都清空事件队列，
而一帧可能跑 2~4 个子步。实测让球穿过一个传感器（应当收到「进入 + 离开」两个事件）：

| 读法 | 收到的事件数 |
|---|---|
| 每个子步读一次 | 2 |
| 只在帧末读一次（改之前的行为） | **0** |

一次完整的穿越**一个事件都收不到**。而那个阶段的文档还写着「挂在这里的系统正好读碰撞事件」。

**改法**：
- 新增 `Stage::FixedUpdate` 与 `Plugin::fixed_update`，在每个物理子步**之前**跑；
- `Stage::Physics` 改成在每个子步**之后**跑，不再是每帧一次；
- 两个定长阶段里 `ctx.dt` **恒等于物理步长**，不是帧间隔——
  在 `FixedUpdate` 里写 `v * ctx.dt` 却拿到帧间隔的话，定长调度就白做了，
  那正是它要消除的东西。

一帧可能跑 0 次（帧率高于步频）、1 次或多次（掉帧后追帧）。

**验收**（demo 里按窗口统计，`--stress` 压低帧率做对照）：

| 帧率 | 窗口内渲染帧 | 窗口内物理子步 | 步/秒 |
|---|---|---|---|
| 60 FPS | 301 | 301 | **60.0** |
| ~28 FPS | 142 | 301 | **60.1** |

帧数差一倍，子步数完全一致——这才叫定长。
（第一个统计窗口总是偏低，那是加载期几帧超长间隔被死亡螺旋保护截断的结果，
不是调度失效；所以 demo 报的是**窗口内**速率而不是从启动累计。）

**未做**：角色控制器（`KinematicCharacterController`，爬坡/台阶/贴地那一套）、

2D 物理、软体与布料、多线程求解（rapier 支持，但要接 ktask 而不是它自带的 rayon）。

#### 阶段 5：动画 ✅ 已完成

新增 `kanim`（2647 行含测试，77 项测试）+ 各 crate 的接入。
连同接入侧的测试共新增 144 项，全量测试 473 → 617。参照规模：`fyrox-animation` 6722 行。

- [x] **骨骼 / 蒙皮** ✅ — glTF 导入 `skins`（关节 + 逆绑定矩阵）与 `JOINTS_0/WEIGHTS_0`；
      `Mesh` 增加**可选的**蒙皮顶点流（`Uint16x4` 关节 + `f32x4` 权重，24 字节/顶点）。
      单独一路顶点缓冲而不是塞进 `Vertex`：静态网格占绝大多数，
      让它们每个顶点白背 24 字节不划算。
      GPU 侧是标准线性混合蒙皮（与 Bevy 的 `skin_model` 一致）：
      `模型矩阵阵 = Σ 权重ᵢ × 骨骼矩ᵢ`，骨骼矩阵 = `关节世界变换 × 逆绑定矩阵`。
      **阴影 pass 也做了蒙皮**，否则角色动起来了、影子还保持绑定姿态。
- [x] **动画剪辑与播放** ✅ — Step / Linear / CubicSpline 三种插值（与 glTF 规范一一对应）；
      循环、倒放、速度、多剪辑加权混合（增量归一化，最终等于加权平均）。
      四元数插值走最短弧，混合时处理双重覆盖（`q` 与 `-q` 是同一个旋转）。
- [x] **状态机** ✅ — 状态 + 带过渡时长的转移 + 参数条件（布尔/浮点比较，可与或非组合）。
      过渡进行中不接受新的转移请求：条件在阈值附近抖动时，
      否则状态机会反复横跳，动画看起来像卡住。
- [x] **混合树** ✅ — 固定权重混合 + 一维混合空间（按参数在相邻采样点间插值）。
      可任意嵌套，权重逐层相乘，总和恒为 1（有测试锁定）。
- [x] **IK** ✅ — 双骨闭式解（余弦定理），够不着时朝目标伸直；
      极向量控制弯曲方向；权重可淡入。已接进场景图（`Scene::solve_two_bone_ik`），
      世界空间的解会被正确换算回局部旋转——父节点带旋转时也对（有测试锁定）。
- [x] **Morph Target** ✅ — 用 `assets/lion.glb` 验证（4 个网格各带一个形变：
      mouth / leftEye / rightEye / tongue）。

      **数据**：`Mesh` 增加形变目标（逐顶点的位置 + 法线增量）与默认权重；
      目标名字从 `mesh.extras.targetNames` 读——glTF 规范没给它专门的字段，
      只能从扩展数据里挖，读不到就退回 `Target0` 这样的占位名。

      **权重存在节点上而不是网格上**：网格是共享资源，
      同一张脸的两个实例要能各做各的表情。

      **动画**：glTF 的一个 `weights` 通道同时驱动 N 个目标、采样值交错排列，
      导入时拆成 N 条标量轨道。这样曲线的值类型保持定长，
      混合逻辑不必为「变长数组」再开一套。三次样条每帧存三份，拆的时候要多除一次。
      姿态里形变权重用**稀疏表**（带形变的网格通常只有几个，
      而各网格的目标数量又各不相同，稠密存会浪费掉绝大部分空间）。

      **GPU**：所有带形变的网格的增量拼进一个只增不减的存储缓冲，
      排成**顶点优先**（`[顶点0的所有目标][顶点1的所有目标]…`）——
      着色器读一个顶点的全部形变只碰一段连续内存；按目标优先排的话，
      每多一个目标就要跳一次整段顶点数据。权重逐实例、逐帧重写。
      顶点着色器里跳过权重为 0 的目标：一张脸几十个表情通常只有几个在起作用。

      **形变发生在蒙皮之前**：形变改的是绑定姿态下的网格形状，
      骨骼再把这个形状带到世界里；顺序反了，张嘴的幅度会被骨骼的缩放放大。
      **阴影 pass 也做了形变**，否则张开的嘴投出来的影子还是闭着的。

      **包围盒**：形变会把顶点推出绑定姿态的范围，逐顶点重算太贵，
      改成给每个目标预存增量范围，运行时按「权重 × 增量范围」把基础包围盒撑开——
      结果偏保守，但剔除只怕小不怕大（有测试对着实际顶点验证）。

      **未做**：切线增量（`TANGENT` 目标）；稀疏 accessor 由 gltf crate 自动展开成稠密，
      目标很多的模型会比较占内存。

**关键设计**（取自 Fyrox 的 `AnimationPose`）：**姿态是混合的中间产物**。
剪辑采样出姿态、混合树合成姿态、状态机在姿态间过渡，最后才由场景图写进节点的局部变换。
状态机与混合树都**不产出姿态**，它们只回答「这一帧每个剪辑占多少权重」，
混合那一步全局只有一份实现——于是整套逻辑能在没有场景、没有 GPU 的情况下测试。

剪辑用 `Arc` 共享：同一个模型实例化多份时，各实例只多出播放进度，
不重复存关键帧（Soldier 光曲线就有几百 KB）。

**一帧的顺序**（顺序错了动画会慢一帧或原地不动）：

```
插件 update → tick_animations（写局部变换）→ update（算世界变换 → 骨骼矩阵 → 包围盒）
            → tick_particles → 剔除 → 渲染
```

`Scene::update` 因此拆成三趟：世界变换 → 骨骼矩阵 → 包围盒与剔除结构。
骨骼矩阵必须等整棵树的世界变换都算完（关节可能在树上任何位置），
包围盒又必须等骨骼矩阵算完（蒙皮网格的范围由关节位置决定，
绑定姿态的包围盒是不会动的，角色一抬手就会被误剔除）。

**验收结果**：`assets/Soldier.glb`（49 关节 / 4 个动画 / 156 通道）
导入、蒙皮、播放全链路打通；`assets/lion.glb`（4 个形变目标）形变链路打通。
demo 里按 1/2/3 在站立、行走、奔跑之间切换（移动状态内部是「速度 → 走/跑」的
一维混合空间），按 M 开关狮子的形变张合。

两个模型都进场后，渲染统计从 36 绘制 / 28882 三角形变为 43 绘制 / 48226 三角形，
绘制调用 9 → 16（蒙皮一批、狮子的 5 个网格各一批），帧率仍是 59 FPS。

**测试覆盖**：真实文件的导入（关节数、逆绑定矩阵、权重归一化、动画覆盖全部关节；
形变的目标名、默认权重、增量真的移动顶点）、
绑定姿态下蒙皮矩阵为单位阵（检查逆绑定矩阵方向最直接的办法）、
动画推进后骨骼矩阵变化且有限、同种子重放逐位一致、
关节与形变后的顶点都落在包围盒内、多实例共享网格但表情与播放进度各自独立、
形变增量的顶点优先排布（最容易搞错的一处，单独抽成纯函数验证）。

#### 阶段 6：音频 ✅ 已完成

新增 `kaudio`（1989 行含测试，78 项测试）+ `kscene` 的声源组件（574 行，13 项测试）。
新增测试 91 项，全量单元测试 871 → 962（另有 49 项文档测试）。
参照规模：`fyrox-sound` 5131 行。

- [x] **选型** ✅ —— **cpal 出声 + symphonia 解码 + 自己写混音与 3D 定位**。
      三个候选都试过对比，结论按这个项目一贯的取舍来：

      - **OpenAL** 出局，理由与阶段 4 拒绝 Jolt 完全相同：C 库、要 FFI、
        会给整个工作区引入 C 工具链。
      - **kira** 出局。它确实好用，但它会把整个音频图接管过去，
        本层就只剩「把节点变换翻译成它的 emitter」——而**混音、距离衰减、
        声像**恰恰是 `fyrox-sound` 那五千行的主体，也正是 kpbr / kanim /
        kparticle 一路自己写的那类纯计算。
      - 真正平台相关、不该自己写的只有两件事：**把样本递进声卡**（cpal，
        地位等同 krender 之于 wgpu）与**解码**（symphonia，等同 ktexture
        用现成的 PNG / JPEG 解码器）。

      这么分还有一个硬性好处：**测试不需要声卡**。混音与定位是纯数学，
      78 项测试里只有 1 项碰真实设备（而且它的断言是「有没有声卡都不能崩」）。

- [x] **音效播放与混音** ✅ —— 声源支持音量、音高（同时变速）、循环、
      暂停/继续/停止/跳转；播完的非循环声源**自动回收**，调用方不必自己收尸。
      源采样率与设备采样率不一致时按比例重采样，播放头落在两帧之间就线性插值。

      **播放头用 `f64`**：`f32` 的尾数只有 24 位，48 kHz 下播到第 350 秒就开始
      丢整数精度，一首歌还没放完音高就飘了。

      **增益在块之间要过渡**：距离衰减与声像每块算一次而不是每样本算一次
      （后者要为每个样本做一次开方和两次三角函数）。但直接在块边界换增益会
      「咔」一声，所以块内把增益从上一块的值线性滑到这一块的目标值。
      几行代码换掉一整类爆音，有测试逐样本验证过渡是单调的、且**第一块不淡入**
      （否则每个音效开头都会多一段不该有的渐强）。

- [x] **3D 空间音频** ✅ —— 三种距离衰减模型（线性 / 反比 / 指数）+ 等功率声像。

      **等功率而不是线性声像**：线性声像在正中间时两声道各 0.5，总功率只有单侧
      的一半，声音扫过中间会有一个明显的「塌陷」。等功率下 `L² + R²` 恒为 1，
      有测试沿整条扫描曲线逐点验证这个不变量。

      **近距离必须夹住**：不夹的话贴到声源上音量会冲向无穷，玩家走过去会被震一下。
      三种模型都有「在参考距离处最响」「再近也不会更响」「全程单调下降」
      「永远落在 [0,1] 内」四条性质测试。

      听者跟着启用的相机走，朝向按 -Z 前 / +Y 上，与相机和 glTF 的约定一致。
      有测试验证「玩家转身，原本在右边的声音跑到左边」。

- [x] **音频流** ⚠️ **未做，见下**

**分层**：`kaudio` 里只有 `device.rs` 碰硬件（cpal），只有 `decode.rs` 碰解码器
（symphonia）。混音器不知道声卡的存在，声卡那侧不做任何 DSP。

**没有声卡时不报错**：拿不到设备就进**静默模式**——所有接口照常工作、声源状态
照常推进，只是没有人来取样本。游戏逻辑因此不必写两套，也不会因为一台没声卡的
机器就起不来。CI 与本地测试走的都是这条路径。

**关于那把锁**：音频回调在独立线程上跑，与游戏线程共享同一个混音器。
在音频回调里加锁通常是禁忌，但这里成立：游戏线程的临界区只是改几个 `f32`，
持锁时间以纳秒计，而音频缓冲有 10 毫秒余量。用 `try_lock` 失败就输出静音反而更糟
——那是**必然听得见**的断音，而等一下几乎必然听不见。`fyrox-sound` 也是这么做的。
`Scene::tick_audio` 因此先在锁外把数据备齐，锁内只做赋值。

**验收结果**：demo 里有一个绕圈的 3D 声源（绿色小球）和 B 键的一次性提示音，
N 键静音。实测输出到真实设备（48 kHz / 2 声道），加音频后帧率 57–59 FPS，
与加之前在噪声内无差异。

**验证到什么程度**：我听不到声音，所以给混音器加了可观测量并在 `C` 的统计里报告。
实测「1 个声源在播；累计 46176 帧，上一块峰值 0.122」——而按参数手算的期望值是
`音源幅度 0.23 × 增益 0.8 × 距离衰减 0.806 × 等功率声像 0.71 ≈ 0.10–0.15`，
实测落在区间内。**样本确实在流动、幅度也对得上**；但「听起来对不对」仍然需要人耳，
这一条我没法替你确认。

**未做**：
- **音频流**（长音乐边解码边播）。现在是整段解码进内存，一分钟 48 kHz 立体声
  约 23 MB——短音效随便放，一张专辑就不行了。做法是把 `AudioBuffer` 换成一个
  能按需喂块的 trait，`Sound` 只认那个 trait；接口已经朝这个方向留了，但没做。
- 混音总线与效果器（混响、滤波、压限）。
- HRTF（双耳渲染）。现在的定位是「音量 + 左右」，听不出前后与高低。
- 多普勒效应。
- 遮挡（声音被墙挡住时变闷）——物理已经就位，射线检测是现成的，但没接。

#### 阶段 7：脚本（JS）✅ 已完成

新增 `kscript`（1683 行含测试，43 项测试）+ `kscene` 的脚本组件（608 行，16 项测试）。
新增测试 62 项，全量单元测试 962 → 1022（另有 50 项文档测试）。

- [x] **选型** ✅ —— **boa（纯 Rust）**。

      `rquickjs` 要编译 QuickJS 的 C 源码，`deno_core` 要 V8 的 C++ 构建。
      而这个工作区到此为止**全是 Rust 源码，`cargo build` 不依赖任何外部工具链**
      ——这条性质在阶段 4（Rapier 而非 Jolt）和阶段 6（cpal 而非 OpenAL）
      各保过一次，没有理由在最后一步放弃。

      boa 慢于 QuickJS 是事实。但游戏脚本通常只占帧时间的很小一部分
      （demo 里两个脚本在 60 FPS 下毫无压力），拿这点性能换整条构建链的简单是划算的。
      真到了脚本成为瓶颈的那天，`kscript` 这一层就是为换引擎准备的。

- [x] **引擎 API 暴露给 JS** ✅ —— 全局 `engine` 对象：
      读 `self / time / find / position / worldPosition / name / visible`，
      写 `setPosition / translate / rotateY / setScale / setVisible /
      applyImpulse / playSound / despawn / log / emit`。

- [x] **脚本生命周期绑定到节点** ✅ —— `init` / `update(dt)` / `destroy`，三个都可选。
      脚本文件是一个**函数体**，`return` 一个带这些方法的对象——写成函数体而不是
      对象字面量，是为了让脚本有自己的**闭包变量**（每实例一份，而不是共享一个全局）。
      源码只解析一次：包成工厂函数，每实例化一次调一次工厂。

- [x] **事件处理** ✅ —— `engine.emit(name, value)` 抛给 Rust 侧，
      插件在 `ctx.script_events` 里读。事件带**发出者节点**，在发出的那一刻记下来
      ——命令是攒到一帧末才一起回到 Rust 的，事后再猜只能猜错。

**架构：快照进、命令出**（初版的决定，**后来被推翻**，见下面「补：改成 GDScript 那样的接口」）

boa 的原生函数必须是 `'static`，把 `&mut Scene` 递进 VM 只有两条路：
线程局部**裸指针**（`unsafe`，别名不变量全靠约定维持），或者把整个 `Scene` 包进
`Rc<RefCell>`（要改掉引擎的所有权结构，波及所有已有代码）。

这里走第三条：tick 开始时把场景拍成**只读快照**递进去，脚本产出一串**命令**，
返回后由引擎依次落地。好处是全程安全 Rust（**零 `unsafe`**）、确定性、
可沙箱、可重放，而且整条链路能在没有 VM 的情况下逐条测试。

代价要说清楚：脚本读到的是**本 tick 开始时**的状态，写入在返回后生效。
对逐帧游戏逻辑这恰好是想要的语义——所有脚本看到同一帧，谁先跑谁后跑不影响结果。
**真正的损失是即时查询**：脚本没法在中途打一条射线、再根据结果决定下一步，
只能把查询排到下一帧。要支持它就得回到 `unsafe` 或 `Rc<RefCell>` 那两条路上去。

宿主状态用**作用域内的线程局部 `RefCell`**递进 VM，靠 `Drop` 收尾（脚本抛异常时
也照样执行——手动收尾的话状态会残留，下一帧读到上一帧的快照，有测试锁这条）。

**跑飞的脚本有三道闸**：
1. boa 的**循环迭代上限**（一千万次）与递归上限——`while(true){}` 会抛异常
   然后那个脚本被停掉，而不是把整个游戏冻死；
2. **命令条数上限**（默认 4096/帧）——`for(;;) engine.log('x')` 会在循环上限
   之前先撑爆内存，超出后丢弃并计数；
3. **出错即禁用**——抛异常的脚本停掉并记一条日志。不停的话它几乎必然每帧都抛，
   日志被刷爆，真正的第一条错误反而找不到了。

另有一道数据闸：**NaN 拦在边界上**。`0/0` 写进位置，世界矩阵会变 NaN，
包围盒随之变 NaN，剔除把它判成不可见——整个物体无声无息地消失，日志里什么都没有。
在提交命令时就拦掉，比事后追查便宜得多。

**节点编号不是 `Handle`**：`Handle` 是 index + generation 共 64 位，塞不进 JS 的
`f64`（只有 53 位整数精度）。改用快照数组的下标，小整数、能精确表示，
而且天然把脚本能碰的节点限制在快照范围内——脚本编不出一个指向任意内存的编号。
节点增删会让编号变，所以每帧重新绑定（有测试专门删掉前面的节点来验）。

**运行时不放在 `Scene` 里**，而是像 `AudioDevice` 一样由 `kapp` 持有：
boa 的 `Context` 不是 `Send`，塞进 `Scene` 会让整个场景失去跨线程能力，
而并行剔除正依赖这一点。

**验收结果**：demo 里两个方块由 JS 驱动——橙色的自转 + 上下浮动（闭包状态、
读自己的位置再写回去），蓝色的绕着它转（跨节点访问 `engine.find` + 世界坐标）。
每两秒脚本抛一个事件，Rust 侧收到并打印，来源是真实节点句柄。J 键开关脚本。
加脚本后 56–59 FPS，与之前在噪声内无差异。

**顺带修掉一个真 bug ★**：写脚本的冲量测试时发现，**新建刚体的当帧施加冲量会被静默吞掉**。
原因是同步顺序——刚体先建好、排队的冲量当场 flush，而碰撞体要到下一步才加上，
那时刚体质量还是 0，而 rapier 的 `Δv = 冲量 × 质量倒数` 在质量为 0 时倒数也是 0。
不报错、没有任何迹象，症状是「新生成的物体第一帧推不动、第二帧起又正常」。
抛射物、爆炸击飞这类「生成即施力」的用法全中招。
修法是把动作的 flush 挪到碰撞体建完之后，已加回归测试。
这个 bug 在阶段 4 就存在，是脚本测试把它逼出来的。

##### 补：改成 GDScript 那样的接口 ✅

初版 kscript 是「快照进、命令出」：脚本读一份只读快照、产出一串命令、帧末统一落地。
那是为了避开 `unsafe` 选的，代价当时也写清楚了——**放弃即时查询**。
后来要求接口与 GDScript 效果相同，这条就必须换掉。

**换掉了什么**

| GDScript 的写法 | 初版 | 现在 |
|---|---|---|
| `self.position.y += delta` | ❌ `engine.setPosition(node, x, y, z)` | ✅ 原样可写 |
| 写完立刻读得到 | ❌ 帧末才落地 | ✅ 下一行就读得到 |
| `get_node("X").position = v` | ❌ 只能拿到数字编号 | ✅ 拿到对象 |
| `_ready` / `_process` / `_physics_process` | ⚠️ 只有 `init`/`update` | ✅ 三个齐全 |
| `Vector3` 与它的方法 | ❌ 裸 `{x,y,z}` | ✅ 完整一套 |
| **即时射线检测** | ❌ 架构上做不到 | ✅ `raycast(from, dir, dist)` |

**实时访问怎么做到的，而且仍然零 `unsafe`**

tick 期间把 `Scene` 连同宿主状态用 `mem::swap` **整个搬进**线程局部，跑完再搬回来。
搬的是 6 KB 的结构体本身（堆上的节点池、物理世界一个字节都不动），一来一回两次 memcpy。
原生函数于是拿得到真正的 `&mut Scene`——不用裸指针，也不用把 `Scene` 包进 `Rc<RefCell>`
去改动整个引擎的所有权结构。

三条不变量都有测试：
1. **搬回去靠 `Drop`**——脚本抛异常时中间的代码会被跳过，手动搬回的话场景就永远
   留在线程局部里，调用方拿到个空壳，整个游戏静默失效（比崩溃还难查）。
2. **借用期间不碰 VM**——访问闭包拿不到 `Context`，结构上不可能在持有借用时回调进 JS。
   万一真重入，`try_borrow_mut` 返回 `None` 而不是 panic。
3. **状态属于运行时，不属于线程**——节点登记处随宿主一起进出。
   这条是**并行跑测试时炸出来的**：初版把登记处放在线程局部长住，
   同一条线程上先后跑的两个测试互相看到了对方的句柄，单独跑全过、一起跑就错。

**分层反了过来**：现在是 kscript → kscene（脚本要实时读写场景），
kscene **不认识**脚本引擎，节点上只留一个存路径的槽位（`ScriptSlot`）。
好处有二：boa 仍然只有一个 crate 认识；槽位里只有字符串，
**脚本因此能随场景存档**——这修掉了初版列在「未做」里的一条。

**手感层放在 JS 里**：Rust 只提供扁平的原生函数（取一个数、写一个数、打一条射线），
`Node` / `Vector3` / `BoundVector3` 这些类由一段前奏脚本定义。
getter/setter、类、链式方法在 JS 是母语，用 boa 的对象 API 拼同样的东西要多写十倍代码。

其中 `BoundVector3` 是 `self.position.y += delta` 能成立的关键：`position` 返回的是一个
**绑定到节点的代理**，不是副本。返回副本的话 `.y += 1` 改的是那个临时对象，写完就丢——
脚本看起来在动、物体纹丝不动，而且不报错。

**与 GDScript 唯一无法弥合的差别**：JavaScript **没有运算符重载**，
所以向量只能写 `a.add(b)`，写不出 `a + b`。这是语言层面的，换不掉（除非换语言）。

**验收**：40 项 kscript 测试覆盖属性读写透传、同一回调内读到刚写的值、跨节点操作、
即时射线、`queue_free` 立即生效、NaN 拦截、死循环停机、坏脚本隔离。
demo 里蓝色小块每帧朝脚下打射线，实测输出「脚下 1.00 米是 PhysicsGround」——
当场拿到结果、当场认出物理地面，这正是初版架构做不到的那件事。

**脚本以磁盘文件的形式存在**（`assets/scripts/*.js`），走 `ScriptLoader` 异步加载，
节点上只记路径。因此它们既能随场景存档，也能热重载。

**与原计划的一处偏离 ★**：原计划写着「`kcore` 的反射系统是把引擎对象暴露给脚本的
基础——`type_uuid` 目前只被生产未被消费，脚本层会是它的第一个真正用户」。
**实际没有用上反射。** 快照/命令这套架构里，脚本能碰的东西是一份**显式的白名单**
（`NodeState` 的六个字段、`Command` 的十一种操作），不需要在运行时按类型信息
去发现字段。这样更安全（脚本碰不到没被显式暴露的东西）也更快，
但代价是**每加一个可脚本化的属性都要手写一遍**——真要把材质、粒子、动画参数
全暴露出去，反射会重新变得划算。`type_uuid` 因此至今仍然只被生产、未被消费。

**未做**：
- ~~即时查询（射线检测等）~~ —— **已在重写中解决**，见上。
- ~~热重载脚本~~ —— **已做**：`ScriptRuntime::reload_path` 把用到该文件的实例
  全部作废，下一帧按新源码重建，顺带把「上次语法错误」的标记清掉
  （改错→存盘→报错→改回来是最常见的用法）。
  实测游戏跑着的时候改 `assets/scripts/spinner.js`，两秒内 `_ready` 重新执行、
  新逻辑生效，游戏没重启。
  **脚本内部状态会丢**（闭包变量回初值）——这是取舍不是 bug，已写成测试；
  要保住得让脚本自己实现存取接口。
- **脚本序列化**——节点上的槽位（脚本路径）现在能随场景存档了，
  但脚本**内部的闭包变量**存不下。要支持得让脚本自己实现
  `serialize()` / `deserialize()`，接口没定。
- 模块/`import`、协程（`async`）、脚本调试器。
- API 覆盖面仍然很窄：动画、粒子、精灵、音频参数都还没暴露给脚本。

### 二、还缺什么

#### P0 — 挡着做游戏

##### 1. 角色控制器 ← **最该做的一件事**

`kphysics` 里没有（`KinematicCharacterController` 一个字都没接）。

这是目前最大的空洞。引擎现在能渲染、能物理、能 UI、能地形、能 2D，
**但没法让一个角色好好走路**。用刚体硬凑永远不对劲：

- 爬不上台阶（矮台阶会把胶囊卡住）
- 斜坡上会慢慢滑下去（静摩擦不是这么用的）
- 撞墙时会打转或弹开，而不是贴着墙滑
- 跳跃手感僵，因为速度是求解器给的不是你给的

rapier 自带 `KinematicCharacterController`（贴墙滑动、自动爬台阶、
斜坡限制、下坡吸附），接进来是有明确边界的一块工作。

**这是「技术演示」和「能做游戏」的分界线。**

2D 那边同样需要一份 —— 平台跳跃游戏的手感全在这上面。

##### 2. 音频流

`kaudio::decode` 现在是 `decode(bytes) -> AudioBuffer`，**整段解码进内存**。

一首 3 分钟 44.1 kHz 立体声 BGM 解码成 `f32` 后约 60 MB。几首就顶不住，
一张专辑必爆。

**任何有背景音乐的游戏都会撞上这个。** 上一版把它放在 P2 的零碎欠账表里，
低估了 —— 它不是"锦上添花"，是"有 BGM 就必须有"。

要做的是：解码器改成按块拉取、播放时后台线程预读、`AudioBuffer` 分成
「整段」和「流式」两种。

##### 3. 拾取

确认没有。现在只能靠物理射线 —— 意味着**没挂碰撞体的东西点不到**。

###### 界面贴图：`Ui` 根本没暴露 `image`

`DrawList::image` 一直都在，`Renderer::register_ui_texture` 也一直都在，
但**中间那一段是断的**：

- `Ui` 上没有 `image` 方法，游戏画不了；
- `Renderer` 不经过 `Context` 暴露，游戏也传不上显存。

所以在这次之前，**kengine 的界面里放不了任何一张图**——没有图标、没有

（6 个例子）都压在这上面。

- `Ui::image` / `Ui::image_fit`（后者保持长宽比、居中、留白）；
- `Ui::register_texture` / `Ui::textures()`，渲染器每帧扫一遍，

`image_fit` 用的是 contain 而不是 cover：图标被裁掉半个角比留一圈白

###### 嵌套滚动区仍然不做，理由写清楚

`WidgetUi` 里滚动区是 `Option<ScrollFrame>`，同一时刻只有一个。
顺着写几个没问题，嵌套不行。

补它要的不只是把 `Option` 换成栈：滚轮该归哪一层、里层滚到底之后要不要
把剩下的滚动量交给外层（scroll chaining），这些规则得先定。而**真实的
游戏界面基本不嵌套滚动区**——嵌套滚动在网页上就是公认难用的东西。

###### 路上撞到的一处：taffy 的跨列写法是有方向的

`grid-column: span N` 展开成 `grid-column-start: span N; grid-column-end: auto`。
写反成 `start: auto, end: span N` 的话 taffy **不报错，跨列静默失效**——
标题老老实实挤在第一列里。测试是先红后绿抓到的。

##### 7d. GPU 粒子 —— 改动比预想的小一个量级

**我原来那条笔记写错了。** `next.md` 里写着「渲染管线只认 `Mesh` 和
`Texture` 资源，算出来的 storage buffer 没法直接当顶点源」——翻代码之前的
臆测。实际上粒子管线**一直**是这个形状：

```rust
// group(1) binding(0)：array<Particle>，只读 storage
pass.draw(0..6, first..first + count);   // 六个顶点拼一个方片，没有顶点缓冲
```

方片在顶点着色器里靠 `vertex_index` 长出来。所以缺的只是**让渲染器用
别人给的那块缓冲**，而不是它自己每帧 `write_buffer` 填的那块。

做的三件事：

1. `StorageBuffer` 加一个 `id`（wgpu 的 `Buffer` 没有稳定可比的标识），
   渲染器按它缓存绑定组；
2. `ParticleBatch` 多一个「数据从哪来」，`draw` 按它选绑定组；
3. `Particle` 的 WGSL 声明从 `particle.wgsl` 拆成
   `kparticle::PARTICLE_STRUCT_WGSL`，让计算着色器**拼同一份**而不是手抄。

###### 两条必须写进文档的限制

- **排序**。粒子是半透明的，alpha 混合不可交换。CPU 粒子由渲染器逐个
  从远到近排，GPU 粒子在 CPU 上没有位置，排不了。所以**只有加法混合
  一定对**；要 alpha 又要正确，得自己在 GPU 上排好（bitonic sort）再交过来。
  引擎不代劳。
- **包围盒只能游戏给**。它不参与剔除，只参与系统之间的先后。
  CPU 的和 GPU 的排在**同一个序**里——分成两段各排各的话，两类系统之间的
  前后关系就成了「谁在数组里排前面」。

###### 验证

`krender::particle::gpu_tests` 里有一条端到端的：真开一台无头设备、
用共享声明写一遍、读回来**逐字段**核对。字段顺序错了那里立刻能看出来
（比如 `size` 和 `position.z` 换了位置的话 size 会是 3.0）。
实机 `gpu_particles` 例子跑到 16384 个粒子、3 次绘制调用。

##### 7f. 光照 —— 移植 three.js `webgpu_lights_*` 时补的三项 ✅

- [x] **聚簇前向着色** —— 光源上限从 **16 提到 256**，而且片元只遍历
      自己那个簇的名单。划分与分配在 `klight::cluster`（纯 CPU、可单测），
      下标公式在 `klight::cluster.wgsl`（CPU 和着色器**共用同一份**）。
- [x] **光照分层**（选择性光照）—— 灯和物体各带一个 `u32` 位掩码，
      按位与非零才照亮。掩码跟着**对象**走，所以「这盏灯只照角色」
      不打断合批。
- [x] **`Light::hemisphere`** —— `LightKind::Hemisphere` 早就有，
      但没有构造函数，用它得手写 `LightKind`。

###### 聚簇的三条取舍

1. **方向光和半球光不进簇。** 它们没有位置也没有范围，照亮一切；
   塞进簇里等于每个簇都有它们。所以光源数组分成两段，着色器无条件
   遍历前一段、按簇遍历后一段。
2. **在 CPU 上分配。** 计算着色器更快，但要多一条依赖链
   （分配 → 屏障 → 着色），调试只能靠读回缓冲。CPU 这边是纯函数，
   每条规则都能写成测试。
3. **一个簇最多 256 盏，超出计数不静默。** 不封顶的话一个病态场景
   （灯堆在同一个角落）能把名单缓冲撑到几十兆。

###### 实测：聚簇省了多少

关掉垂直同步、256 盏灯（512 盏里被上限截掉一半）：

| | 帧时间 |
|---|---:|
| 聚簇开 | **3.30 ms** |
| 聚簇关 | **4.31 ms** |

省下的约 1 ms 基本就是光照循环的全部——256 盏 × ~92 万片元 ≈ 3.7 G 指令，
量级对得上。同一帧里每簇平均 **2.8 盏**（128 盏灯时），
相对全遍历是 45× 的削减。

**这个数比想象的小**，因为这个场景几何很轻、窗口也不大，光照循环
只占一帧的四分之一。真正吃亮度的场景（大量重叠光源 + 高分辨率）
差距会大得多。数字照实记，不往大了说。

###### 路上抓到的一处：**浮点重排让两边算出不同的簇**

第一版的对拍测试要求「CPU 和着色器算出同一个下标」，第一次跑就红了：

```
像素 (960.0, 540.0)：CPU 说 8，着色器说 7
```

诊断出来的原因是 `960 * 16 / 1920` 在这块 GPU 上算出的是 **7.9999995**
——驱动把它重排成了「乘以倒数」。改成先乘后除也没用，驱动照样重排。

这不是「两边写得不一样」，**是浮点重排本来就不受源码控制**，
换块显卡结论可能就变。所以不去赌位级一致，改成让正确性不依赖它：
CPU 分配时把每盏灯的块范围**往外扩一格**，边界上两边选哪边都取得到。

测试的契约也跟着改了，从「相等」改成真正要紧的那条：

> 片元被某盏灯照到时，着色器挑中的那个簇里必须有这盏灯。

`krender/tests/cluster_agreement.rs` 里那条端到端的就是验这个：
造一批灯、CPU 分配、取每盏灯照得到的点、算出像素坐标喂给真 GPU，
再回头查名单。

###### 顺带修掉：**测试全绿但进程崩了**

`cargo test -p krender --lib` 三次里有一次以
`STATUS_STACK_BUFFER_OVERRUN` 退出——**在「145 passed」之后**。
测试报告全绿，退出码却是失败。

原因是每条 GPU 测试各建一台无头设备，libtest 并行跑时几十台设备
同时创建又同时析构。改成整个进程共用一台（`ComputeContext::shared`，
`OnceLock` 持有到进程结束，**故意泄漏**——测试进程本来就要退出，
而泄漏一台设备换掉的是「绿了但崩了」这种报告）。

五次连跑干净，而且从 6 s 降到 **0.7 s**：建设备本来就是这些测试里最慢的一步。

**后来发现只修了一半。** 那次改的是 `pub(crate) fn shared()`，只管得着
crate 内部的测试。`tests/` 下的集成测试各自是独立的 crate，够不着它——
于是 `cargo test --workspace` 跑到 `tests/compute_life.rs` 时又崩了一次，
同样是「没有任何 `test result: FAILED`，只有一行 `error: test failed`」，
也就是进程级崩溃而不是断言失败。单独跑那个二进制六次全过，只有并发时才炸。

改成 `pub fn shared_headless()`，四个集成测试（`compute_life`、
`example_shaders`、`cluster_agreement`、`area_and_cookie`）都换过去。
这条记在这里是因为**症状太容易被当成偶发而放过**：它不改测试报告的内容，
只改退出码。

##### 7g. cookie / 面光源 / 光照探针 —— 做完了 ✅

7g 原本是「three.js 光照那批里还没做的」清单，前三项已经做掉。

**1. 聚光灯的 cookie 贴图**（`lights_spotlight` / `lights_projector`）

一张纹理数组，整个场景共用（`Scene::set_cookie_atlas`），灯上存层号
（`Light::with_cookie`，存的是 layer+1，0 表示没有）。片元把着色点投影到
光的成像平面，除以外锥在那个距离上的半径得到 UV，采出来的 RGB 直接乘进
辐射亮度。

用图集而不是「一盏灯一张纹理」，是因为后者要么把光源拆成一盏一次绘制，
要么给每盏灯一个绑定组——两条都和这个引擎的合批方式冲突。代价是所有
cookie 必须等大。

`GpuLight` 因此从 80 字节涨到 96：多了一个 `right`（世界空间的右轴，
UV 的两根轴要靠它）和一个预算好的 `tan(outer_angle)`。

**2. 矩形面光源**（`lights_rectarealight`）

**没有用 LTC**。LTC 要两张离线拟合的 64×64 查找表，而这个引擎没有生成
它们的办法。走的是另一条：

- 漫反射用多边形形状因子的闭式解（Lambert 1760）——这一半是**精确的**，
  LTC 也只是在逼近它。
- 高光用代表点近似（MRP）——这一半是近似的，掠射角下高光会比真实的短。

也就是说亮度分布是对的，高光形状在极端角度下不如 LTC。这个取舍是被
「拿不到那两张表」逼出来的，不是偷懒。

原来 7g 里写「这批里最贵的一个」——**判断错了**。真正贵的是 LTC，
而绕开 LTC 之后这一项比 cookie 还小：漫反射的闭式解只有十来行。

**3. 光照探针**（`lightprobe`）

原来写的是「球谐那一半已经有了，缺的是探针物体」，这话**只对了一半**。
球谐确实有，但**全场景只有一组**：`ibl_diffuse` 永远读
`globals.environment.sh`。而反射探针那一半早就是逐探针的了。结果是
红房间里的白墙被室外的天空照亮，而它旁边金属球的反射却是对的——
反射对了，环境光还是错的，且后者在粗糙表面上占比更大，反而更显眼。

补的东西：`ReflectionProbeEntry` 多一组自己的球谐（和 mip 链出自同一张
图），渲染器把它们打进 group(0) binding 4 的一块存储缓冲，
`ibl_diffuse_from_sh` 按物体的探针层号去取。层号和镜面那边用的是
**同一个**（`ObjectUniforms.probe_position.w`），两半不会脱节。

顺手补的口子：`HdrImage::from_pixels` / `HdrImage::from_fn`。原先
`HdrImage` 只能从 `.hdr` 字节流解码，而程序化天空、立方体相机当场采到
的环境、离线烘出来的探针都拿不到字节流。

**测试抓到的真 bug**

`src/krender/tests/area_and_cookie.rs` 拿数值积分当参照验形状因子，
第一次跑就红了：光源空间的「上」轴写成了 `cross(forward, right)`，
在右手系里那是**下**轴。两个后果——cookie 的图案上下颠倒，
矩形四个角的绕序反了导致形状因子整个是负的、被 `max(.., 0.0)` 钳成 0。

后一个尤其值得记：**面板一盏光都不发**，看起来像「忘了打开这盏灯」
而不像 bug。而且我第一次修的时候改的是角点顺序——那能让测试变绿，
但上轴还是错的，cookie 的 v 仍然是反的。两个错叠在一起时形状因子
是正的，只有把 cookie 的 v 一起验了才暴露出真正的根因。

##### 7g-2. IES 与环境捕获 —— 做完了 ✅

**1. IES 配光曲线的解析**（`lights_ies_spotlight`）

`klight::ies`：读 IESNA LM-63 的角度-光强表，烘成一张 cookie 贴图。
引擎这边**没加新的光照路径**——IES 也好、窗格也好，都只是 cookie 图集
里的一层。

格式最要命的一条：数值只按**空白**分隔，和换行完全无关。同一份数据，
有的文件一行一个角度，有的把三千个坎德拉值挤成十几行。按行写的解析器
在半数文件上能跑，剩下半数读出一堆垃圾——而垃圾光强不报错，只是灯的
形状不对。所以先把整个数值区切成词流再按位置读。

对称性是靠水平角的**跨度**隐式声明的，没有单独字段（一个角 = 旋转对称，
0–90 = 四象限，0–180 = 左右，0–360 = 完全不对称）。折错了灯会左右颠倒
或转 90°，同样看不出来。四种都实现了。

半径和角度的关系是 `θ = atan(r · tan(cone))` 而不是 `θ = r · cone`。
线性写法在小角度下几乎看不出差别，大锥角下光形被压扁——有一条测试
专门把这条钉死，而且顺带验了「线性和正切在那个配置下确实分得开」，
否则那条测试就是摆设。

测试拿的是仓库里**四份真的厂商文件**（`examples/threejs/ies/`）。
合成的样例只验得了「我以为的格式」。

没做：TILT 的倾斜修正（正确跳过但不参与计算，它是安装参数不是光形）、
B 型和 A 型光度学（按 C 型采样，形状会歪；`photometric_type()` 暴露出来
让调用方自己判断）、`.ies` 文件本身没有嵌进引擎的资源包格式。

**2. 立方体相机 / 场景环境捕获**（`lightprobe_cubecamera`）

`Renderer::capture_environment` / `Context::capture_environment`：
站在一个点往六个方向各渲一遍，拼成一张等距柱状 HDR，可以直接喂
`set_environment_hdr` 或 `add_reflection_probe`。

在这之前探针**照不出场景**：环境图只能是现成的 `.hdr` 或程序生成的，
和场景是两份各自维护的东西，对不上也没人会告诉你。

改动比预想的小：主 pass 本来就画在离屏 HDR 目标上，只有后处理才碰
交换链。所以只要把 `render` 里三处变成参数——相机从哪来、要不要画 UI、
画完往哪送——就够了。捕获时不走后处理（色调映射会把亮部压掉，
反射里的高光就没了）、不画 UI、不碰交换链。

三条陷阱都写在文档里了：探针自己那个物体要先藏起来**并且重算一次
可见性**（漏了捕出来一片黑，不报错）；一次弹射（第二次捕比第一次准）；
面的正交基必须和渲染时的视图矩阵完全一致（有测试逐分量比对）。

###### 顺带修掉：**改一次窗口大小卡 190 毫秒**

捕获第一版实测 500 ms，而且**和面的尺寸无关**——16 的面和 256 的面
一样慢。加计时一测：六次渲染只占 11 ms，回读 2.5 ms，两次
`rebuild_scene_bind_groups` 占了 400 ms。

罪魁是 `create_brdf_lut` 在 CPU 上重算 BRDF 积分查找表（64×64 蒙特卡洛，
约 95 ms），而那张表**是个常量**，只和一个 `const SIZE` 有关。
一次重建要造两个绑定组（不透明和半透明各一个），所以 190 ms。

而重建绑定组的时机有：改窗口大小、换环境图、换 cookie 图集、开关 SSAO。
也就是说**拖一下窗口边框就卡将近两百毫秒**，而这件事没有任何症状指向
查找表——它只表现为「这引擎缩放窗口好卡」。

拆成 `SceneStatics`（查找表 + 三个采样器，只造一次）之后：

| `face_size` | 之前 | 之后 |
|---|---|---|
| 64 | 500 ms | 7 ms |
| 128 | 458 ms | 17 ms |
| 256 | 542 ms | 55 ms |

这个 bug 是**被别的工作撞出来的**，不是找出来的：如果不是捕获要连着
调两次 resize、而且慢得离谱到必须去量，它会一直待在那儿。

###### 记一笔：写了个没测过的数

定位过程中我先猜「六次阻塞回读是大头」，改成一块缓冲一次同步，
并在注释里写了「六次同步 500 ms，一次同步 90 ms」。改完一测——
**一点没变**，那个数字是我编的。批量回读本身留下了（六次流水线停顿
换成一次是白捡的），但注释换成了实测值：回读一共 2.5 ms，从来就不是瓶颈。

##### 7g-3. 自定义光照模型做成一等公民 —— 做完了 ✅

材质现在有**两个钩子，都可选**：

| 钩子 | 覆盖什么 |
|---|---|
| `material_surface(surface) -> Surface` | 表面属性：颜色、法线、金属度、粗糙度、自发光 |
| `material_lighting(surface, input) -> vec3` | **一盏灯的贡献**，引擎在它的光照循环里逐盏调 |

覆盖后者等于换掉 BRDF，而阴影、光照分层、聚簇、衰减、cookie、IBL、雾
**全都还是引擎的**。之前那条路是「借道自发光」：在表面钩子里自己遍历
光源、把结果写进 `emissive`、再把 `base_color` 压成 0——能出画面，
但上面那些全绕过去了。`lights_custom` 例子已经改成新写法，切到自写
模型时影子不再消失。

阴影由引擎在钩子**返回之后**乘，而不是交给钩子。理由很直接：
「自定义光照模型顺手把阴影搞丢了」正是这个钩子要解决的问题，
**能忘掉的东西就不该让人去记**。

两个钩子都可选是靠 `hook_defines` 在拼装前扫一遍源码决定的。WGSL 没有
重载也没有弱符号，只能这么判。判错的后果是明确的编译错误（重复定义或
缺定义，naga 都直接报），不会出现「静默用了默认实现」。注释掉的定义
会被算成「用户写了」——已知的粗糙之处，有测试盯着，报的也是编译错误。

###### 表面必须传指针，这是量出来的

第一版 `LightingInput` 里直接放了一份 `Surface`（按值）。跑基准：

| | 256 盏点光源，六次 512² 全渲染（取最小值） |
|---|---|
| 钩子化之前 | 267 ms |
| 按值传 `Surface` | **407 ms** |
| 传 `ptr<function, Surface>` | 259 ms |

`Surface` 有四十多个浮点，而这个函数**每盏灯调一次**。改成指针之后和
「根本没有这个钩子」一样快。代价是钩子里要写 `(*surface).normal`——
丑，但一半的帧时间不是风格问题。

WGSL 不允许结构体成员是指针，所以 `surface` 只能是个单独的参数，
塞不进 `LightingInput`。

这个基准是借 `capture_environment` 搭的：它跑六次**完整**渲染而且不等
垂直同步，正好是一个稳定可重复的主 pass 基准。上一节刚做的东西
顺手当了这一节的量具。

###### 半球光不走这个钩子

它没有方向也不产生高光，是个**环境**项，和 IBL 归在一起由引擎处理。
钩子覆盖的是方向光、点光源、聚光灯、矩形面光源这四种直射光。

##### 7g-4. 五个欠账一次清掉 ✅

7g-4 原本是「还没做」的清单，五项都做了。

**1. 面光源的软阴影**（`lights_rectarealight`）

面光源的影子有一条肉眼立刻认得出的特征：**离遮挡物越远越糊**。
固定半径的 PCF 无论怎么调都给不出这个，它只能给一圈等宽的模糊边。

改成 PCSS：先用 `textureLoad` 在阴影图里找遮挡物有多远（比较采样只会
告诉你「通过没通过」，而这里要的是**距离**），半影按「遮挡物到接收面
的距离 × 面板张角」张开。张角 = 面板半尺寸 / 到面板的距离，所以把面板
调大影子跟着变糊。

**其他类型的灯张角为 0，直接走原来那条固定半径的路**——加这个功能
不改任何已有场景的画面，也不让它们变慢。

半影的世界宽度要换成纹素半径，靠的是从光空间矩阵反解「一个世界单位
几个纹素」。这一步有两条 CPU 测试钉着（`klight::cascade`）：一条对着
实测值，一条**反证**——如果只取 `m[0][0]`（斜光下会错），两者会差
5% 以上，从而证明第一条测试真的测到了点子上。

没做的那一半：阴影图仍按**方向光**渲（沿面板法线的正交级联）。真正的
面光源阴影每个点看到的方向都不一样，平行投影给不出。表现是影子的
**形状**比真实的收敛一点，而半影的**宽度**是对的。面板离场景越远越准。

**2. 探针之间的过渡**（`lightprobe`）

`ReflectionProbe` 多了一个 `blend_distance`：盒子边缘往里那一圈用来和
「外面那个」过渡（罩住它的更大的探针，没有就是全局环境）。权重走
`smoothstep`——线性的话过渡带的**两端**各留一道导数不连续的折线，
在大片平坦的墙上仍然看得出两道边。

球谐在**乘过强度之后**混，混完再当成强度 1 求值：两个探针的强度可以
不一样，先求值再混就得算两遍球谐。

权重为 0 的物体一个字节都不多读，`blend_distance = 0` 完全还原成
原来的硬切换——已有场景不会悄悄变样，有测试守着这一条。

近似的地方：次探针的镜面**不做视差校正**（那要逐对象多两个 vec4）。
过渡带里两个探针本来就挨着，误差小且正在淡出。

**3. IES 的 B 型 / A 型光度学**

LM-63 第 6 个字段说的是「这张表的两个角度怎么解释」，三种是三套坐标：
C 型是极角-方位角（0..180 / 0..360），A/B 是**偏航-俯仰的方格**
（都是 -90..90）。范围不同正是因为参数化方式根本不同——把 A/B 的表当
C 型采，光形会整个扭曲，而画面上只是「这盏灯形状怪怪的」。

三种都实现了。但**仓库里那四份样本全是 C 型**，A/B 只有几何不变量在
守着（光轴上必为 (0,0)；绕各自的极轴转只动其中一个角；三者在斜方向上
必须给出不同的答案——最后这条是防止三个分支其实算的是同一个东西）。
没拿厂商的 A/B 文件对过，这一点写在文档里而不是含糊过去。

**4. 捕获的接缝**

双线性要取四个相邻纹素，而落在面边缘上的那些**有一半在隔壁面里**。
夹到边上会让两个面各自把最外圈往外抹一格，交界处留下一道一格宽的脊。

现在越界的纹素会**到相邻面里去取**：把它的中心方向算出来，交给包含
这个方向的那一面。不需要邻接表——方向本身就说明了它属于谁。

测试验的是**连续性**：只差 0.008 弧度的两个方向，取回来的颜色也该只差
一点点。换回夹边它会红（实测跳变 0.0298，阈值 0.02）。另一条比对解析值
的测试**抓不到接缝**（32² 下夹边的误差还在容差里），这一点在注释里
说清楚了，免得以后有人以为它在守接缝。

**5. 环境光那一半也做成钩子**

第三个钩子 `material_ambient(surface, input) -> vec3`，覆盖半球光 + IBL
的漫反射与镜面。三个钩子**全都可选**。

半球光因此从 `shade_light` 里挪了出来——它没有方向也不产生高光，
留在那儿的话自写光照模型会拿到一个 `light_direction` 毫无意义的「灯」，
算出一片乱七八糟的高光，而且不报错。有测试盯着「`shade_light` 里不许
再出现 `LIGHT_HEMISPHERE`」。

分成两个钩子而不是一个：直射光是「一个方向 + 一次 BRDF」逐盏灯调，
环境光是「整个半球的积分」逐片元一次。合成一个的话每盏灯都要判断一次
「这次是不是环境光」，那个判断在循环里是白付的。

##### 7g-5. 这批光照里**还剩**的

1. **A/B 型 IES 没有真文件可验** —— 需要厂商的 Type A/B `.ies` 才能
   把几何不变量升级成端到端的对照。
2. **面光源阴影用的是平行投影** —— 影子的形状比真实的收敛。真做要给
   面光源一套自己的（透视）阴影图，而现在的阴影子系统只有级联方向光。
3. **探针过渡只混两份** —— 三个探针交叠的角落仍然会跳一次（跳的幅度
   比原来小）。任意多个要每个物体带一串权重，代价随探针数涨。
4. **捕获的跨面取样是最近邻** —— 越界那一格取的是隔壁面的最近纹素而不是
   再来一次双线性。它只占最终结果的四分之一以下，且已经消掉了那道脊。
5. **没有「多重弹射」的自动化** —— 捕获一次就是一次弹射，想更准得自己
   连捕几遍。什么时候够了没有判据。

##### 8. 物理 —— 移植 three.js `physics_*` 时补的四项 ✅

十三个例子里，三个 instancing 和两个 terrain 是同一件事的不同后端，
各自合并成一个；`physics_rapier_basic` 由已有的 `physics_basic` 覆盖。
剩下八个都在 `examples/kengine/new/`。

**1. 接触力事件**（`physics_break`）

碰撞事件只说「这两个碰上了」，说不出**撞得有多狠**——而「轻轻放上去」
和「一炮砸过来」在那里是同一件事。拿它做碎裂判定就是「一挨着就碎」。

补的是 `ColliderDesc::contact_force_threshold` 和
`Scene::contact_force_events`。阈值不是 0/1 开关，是力的**下限**：
碰撞每帧都在发生（一摞箱子静止时每个接触点都有支撑力），给低了会被
自重刷屏。1 千克的物体静止在地上约 10 牛。

**不设阈值一条事件都不会来，而且没有任何提示。** 有四条测试守着这件事，
其中一条专门验「更狠的撞击报出更大的力」——不验的话它可能只是个
「碰上了」的复读机。

顺带补了 `Scene::contact_force_nodes` / `node_of_physics_user_data`：
新的事件类型原本没有解回节点的路。

**2. 射线载具**（`physics_vehicle`）

`kphysics::VehicleController`，包 rapier 的 `DynamicRayCastVehicleController`。
车身是一个普通动态刚体，四个轮子是往下打的射线，场景里那四个轮子网格
**没有刚体也没有碰撞体**。

两个坑都是测试抓出来的：

- rapier 默认车头朝 **X**，而引擎的节点前方是 **-Z**。不改的话车会
  「侧着开」——物理完全正常，只是模型的车头对着侧面。
- 驱动方向是 `地面法线 × 轮轴`。「左右轮给相反的轮轴」看起来天经地义，
  实际会让一边往前推、一边往后推，车斜着**螃蟹步**走。第一版就是这么写的，
  测试报出来「打了方向反而偏得少」才发现。现在有一条**反证**测试：
  故意把轮轴给反，断言车确实会横着跑——否则上面那条就成了摆设。

**3. PBD 软体**（`physics_cloth` / `physics_volume`）

`kphysics::SoftBody`：布料和可压的闭合体积。

不用弹簧的理由：弹簧的**刚度和步长挂钩**，布要想不抻长弹簧就得硬，
一硬显式积分就要极小的步长。60 Hz 下调不出「不怎么抻的布」。
PBD 直接把粒子挪到满足约束的地方，无条件稳定，刚度变成「解算几次」。

三件事写进了文档而不是留给人踩：

- **单向耦合**：布被刚体推开，推不动刚体。质量比太悬殊，加回去的冲量
  要么没效果要么把箱子弹飞。
- **顶点要焊接**：图元在 UV 缝有重复顶点，不焊的话球会从缝上裂开，
  而且不报任何错。
- **阻尼的单位**：第一版把「每秒衰减」实现成了「每帧衰减」，差 60 倍——
  0.5 的阻尼变成每秒衰减到 0.5⁶⁰，布半秒只掉 10 厘米。看起来只是
  「布有点飘」，很容易被当成参数没调好。测试抓出来的。

另外记一笔：验压力的第一版测试是「给所有粒子加同一个向下的速度」，
那是**纯平移**，一点形变都没有，开不开压力跑出来一模一样。改成沿 Y
压扁再看恢复，才真的测到了东西。

**4. 双面材质**（布料要用）

`Material::with_double_sided`。布、树叶、纸片只有一层三角形，剔掉背面
之后从另一侧看就是透明的——而引擎原本**根本没有这个概念**。

剔除模式是管线状态，所以它进了合批的键：单面和双面的对象没法合在一批里。
不比这一项的话，一批里第一个对象的剔除模式会套在整批上——布和地面挨在
一起时，要么布的背面没了，要么地面的背面被白画一遍。两种都不报错，
有测试守着。

双面那一套管线是**懒建**的：绝大多数项目一个双面材质都没有，
而四条管线的编译不是免费的。顺带把「标准 + 每个钩子」那四条管线的
构造抽成了一个 `build_material_pipelines`——原本抄了两遍，加一条管线状态
就要改两处。

###### 顺带补的小口子

- `Collider::heightfield` / `trimesh` / `convex_hull`：场景层原本只有
  ball/cuboid/capsule 三个快捷构造，地形和破碎都够不着。
- `Node::set_rigid_body` / `remove_rigid_body`：网格、材质、碰撞体都有
  setter，唯独刚体只有建造式。

##### 8b. 物理这批**还剩**的

1. **软体是单向耦合** —— 推不动刚体。双向要给软体一个整体质量再分配，
   那是另一套东西。
2. **软体之间不互相碰** —— 只和刚体世界碰。软体互碰要它们自己的空间结构。
3. **碎裂是八等分不是凸切割** —— three.js 那版按撞击点真的切。
   真切割要一套凸包裁剪，是另一个模块的量级；八等分的好处是碎块仍然是
   盒子，碰撞比凸包便宜得多。
4. **载具的阴影图** —— 车身是普通刚体所以有影子，但轮子是纯网格，
   它们的影子来自网格本身，和射线的结果无关（悬挂压缩时对得上，
   因为网格跟着位姿走）。
5. **没有多体关节** —— 长关节链会被拉开一点（信息从末端传到根部要走
   和段数一样多的迭代）。rapier 有多体关节，这个引擎还没包。

##### 7e. 预通道 + SSAO

链路是 `预通道 → 深度 + 世界法线 → SSAO pass → 遮蔽图 → 主 pass`。

**遮蔽乘进 `occlusion` 而不是乘在最终颜色上。** 那一项只作用在
`pbr_ambient` / `ibl_diffuse` / `ibl_specular` 上，所以只削弱环境光，
直射光不受影响。乘在最终颜色上（很多引擎图省事的做法）会把太阳照亮的
地方也一起压暗，看着像整个画面蒙了一层灰。

###### 两个有意的取舍

1. **预通道不复用主 pass 的深度。** 顺序上做得到（它排在前面），但那要求
   主 pass 改成 `LessEqual` + `LoadOp::Load`，而两条 pass 的顶点变换必须
   **逐位相同**才安全——同一段 WGSL 编进两个模块，驱动的优化不保证一致，
   差一个 ULP 就会在物体表面上抠出一片洞。省这一遍是一次独立的、
   有回归风险的改动，不该和「把 SSAO 做出来」混在一起。
2. **默认关着。** 它不像软粒子那样「不开就明显穿帮」，而代价是实打实的
   （几何走两遍）。关着时两个 pass 都不跑，主 pass 绑 1×1 白图——
   「没有 SSAO」于是等价于「乘 1」，着色器不必写分支。

###### 路上撞到的一处

**预通道的着色器光有 `geometry.wgsl` 编不过。** `Globals` 里引用了
`Environment`（kpbr 的 IBL）和 `Light`（klight），那两段必须排在前面。
主着色器走 `material_shader_source` 时已经拼全了，预通道这条路才暴露出来
——现在抽了一个 `geometry_prelude()`，测试和运行期用同一份。

###### 验证：SSAO 的数学真跑了一遍

`ssao_gpu_tests.rs`：喂一组**人造的**深度和法线，读回遮蔽图。
SSAO 是「装了但不生效」的重灾区——半球方向反了、深度反解错了、
范围检查写反了，任何一条都会让整张图恒等于 1（完全没效果）或者恒等于 0
（全黑），而且一句错都不报。五条断言：

| | 验什么 |
|---|---|
| 平坦的墙 | **几乎不遮**（> 0.9）。混进朝向表面内侧的采样方向就会挂 |
| 天空 | 一点不遮。不特判的话反解出来的位置在无穷远，结果是随机噪声 |
| 一级台阶 | **凹的那一侧确实变暗** ← 真正证明「它有用」的那条 |
| 强度为 0 | 效果完全关掉。写成加法或者位置放错就关不掉 |
| 强度 0.5 → 2.0 | 更暗。反过来说明某处符号反了 |

实机 `ssao` 例子：开着 26 次绘制调用，关掉 13 次。

##### 7b. 着色器与材质 —— 移植 bevy `examples/shader` 时补的四项 ✅

- [x] **条件编译**（`kshader::preprocess`）—— `#ifdef` / `#ifndef` /
      `#else` / `#endif`，可嵌套。删掉的行**换成空行**，naga 报错的行号
      才还对得上。刻意不做 `#define`：开关必须从 Rust 侧给，
      否则源码里自己定义的开关对管线缓存不可见——同一份源码同一个 id，
      却编出不同的代码。
- [x] **管线常量**（WGSL `override`）—— `Shader::with_constant` 挂在
      着色器资源上，渲染器建管线时交给驱动。要害是**换常量必须换 id**：
      不换的话第二个变体拿到第一个变体的管线，画面上完全看不出来。
- [x] **纹理数组** —— `Texture::from_layers` + group(2) 的
      `custom_texture_array`（`D2Array`）。这是「一批东西各不相同又要合批」
      的唯一正解：层号是逐实例的参数，绑定组不变。
      **顺带给地形 splat 铺好了路**（P1 第 4 项那个欠账）。
- [x] **计算着色器绑纹理** —— `StorageTexture` + `dispatch_with`
      + `read_texture`。`compute_game_of_life` 的文档里那句
      「只绑 storage buffer，还不能绑纹理」可以划掉了。

###### 路上抓到的两处，都记在测试里

1. **多层纹理的 `D2` 视图必须显式限定**。`TextureViewDescriptor::default()`
   会按层数自己挑维度，多层纹理拿到的是 `D2Array`——绑到 `texture_2d`
   的槽位上会被 wgpu 打回。所以 `GpuTexture` 现在存两份视图。
2. **纹理读回的行对齐**。GPU 拷纹理到缓冲时每行按 256 字节对齐，
   不把填充抠掉的话读回来的图**逐行错位**，看着像被斜切了一刀，
   很容易误判成着色器写错了坐标。`read_texture` 内部处理，
   测试用一张 5×3 的图盯着（每行 20 字节，实际占 256）。

###### 顺带挖出一个存在很久的真 bug：**内置图元的绕序**

移植 `screenspace_texture` 时你发现立方体「只能看到 3 个面」。查下来
比看到的还严重：

| 图元 | 状况 |
|---|---|
| `cube` | **±X、±Y 四个面绕序反了**，只有 ±Z 是对的 |
| `sphere` | **六个方向全反**——看到的是远侧半球的**内壁** |
| `plane` / `cylinder` | 正确 |

绕序反了的面在 `cull_mode: Back` 下**从外面就是看不见的，而且不报任何错**。
立方体因此变成能看穿的空壳；球更隐蔽——翻面之后**轮廓一模一样**，
只是法线全背对相机，光照和深度都是错的，肉眼几乎发现不了。
球这个错大概从写出来那天就在。

**我第一次判断错了方向。** 手算叉积得出「plane 和 cylinder 是对的、
cube 和 sphere 是反的」，但推不出哪套约定才是渲染器实际用的——
WebGPU 判绕序用的是**帧缓冲坐标**（y 向下），而投影矩阵里可能还有
一次 y 翻转，两次翻转抵不抵消靠想是想不出来的。中途还写过一版测试
只查「中心像素有没有被盖住」，**它全绿而且毫无意义**：闭合网格的正面
被剔掉时，背后那个面的内侧照样盖住中心像素。

最后是把法线画成颜色、真渲一遍、读回中心像素解出「画的到底是哪个面」
才定的案。这条留在 `krender/tests/culling_convention.rs` 里。

修法：给每个面挑一组 `r`/`u` 使 `r × u == 法线`，再按
左上 `-r+u`、左下 `-r-u`、右下 `+r-u`、右上 `+r+u` 排角——
展开就是 `(v1-v0) × (v2-v0) = 4n`，绕序必然对，而且同一组 `r`/`u`
顺手把 UV 朝向也定死了（原来那四个面的 UV 还是镜像的）。

两层测试：
- `kmesh`：绕序与顶点法线一致，纯 CPU，**CI 上没显卡也跑得动**；
- `krender/tests/culling_convention.rs`：真渲一遍，六个方向各看一眼。
  另有两条钉住约定本身（地面从上面看得见、从下面看不见）——
  它们挂了说明是渲染器的 `front_face`/`cull_mode` 被改了，
  那会让所有图元一起翻面。

###### 新增的安全网：`tests/example_shaders.rs`

材质钩子是片段，单独解析不了，所以**写错的钩子在跑起来之前一声不吭**，
跑起来也只是日志里一行「退回标准管线」。新加的
`krender::validate_material_hook` 把拼装校验暴露出来，这份测试拿它把
每个例子的 `.wgsl` 都过一遍——`shader_defs` 那个还把 16 种开关组合
全跑了一遍（`#ifdef` 删掉的代码不参与编译，「开着能编过」说明不了
「关着也能编过」）。

##### 6b. 移植 bevy `examples/camera` 暴露出来的、**还没补**的缺口

camera 那九个例子全部移植完了，但最后两个各露出一个洞：

1. **渲染层 + 多相机多趟绘制** —— `first_person_view_model` 只做成了
   一半。手臂挂成相机的子节点这一半没问题；**两台相机、两个 FOV**
   那一半做不到：`Scene::active_camera` 取的是第一台启用的相机，
   一个场景只画一台。
   于是调 FOV 时手会跟着变形，走到墙根前手会被墙剪掉——真实的第一人称
   游戏正是为了避免这两件事才用两台相机的。
   补齐分两块：**渲染层**（节点和相机各带一个位掩码，取交集决定画不画）
   便宜；**多相机多趟绘制**贵，`render()` 是一整块，抽出「渲染到任意
   目标」有真实回归风险（反射探针烘焙卡在同一个地方）。
2. **绘制顺序是死的** —— `3D → 粒子 → 精灵 → 调试线 → UI`，
   所以精灵**一定**在界面底下，`2d_on_ui` 那种「2D 画在 UI 上面」做不到。
   这一条是**有意的取舍**而不是缺口：顺序固定下来之后，
   「为什么我的血条被挡住了」这类问题就不存在了。要画在界面上面，
   就用 `Ui::image` 把它当界面画（例子里两条路并排摆着）。

##### 7c. 移植 bevy `examples/shader` 暴露出来的、**还没补**的缺口

按「挡不挡着做东西」排：

1. ~~真正的深度／法线预通道~~ —— **已做**，见 7e。现在有深度和法线了，
   SSAO 也接上了。**仍然没有运动向量**，所以 TAA 还是做不了；
   屏幕空间反射要的不只是预通道，还有 ray march 和打不中时的回退，
   也还没做。
2. **2D 没有自定义材质** —— `ksprite` 走自己的批处理管线，没有钩子。
   bevy 的 `shader_material_2d` 因此没法移植。2D 想要溶解、描边、
   色阶化都只能改引擎。
3. **读回是同步的** —— bevy 有 `Readback` 组件 + `ReadbackComplete` 事件，
   不阻塞。kengine 的 `read` 调用即等待。要做成异步得有一套「谁来收结果」
   的机制，而没有 ECS 的事件系统，那套东西得另外设计。
4. ~~计算结果进不了渲染管线~~ —— **这条我写错了**，见 7d。粒子那条路
   本来就是从 storage buffer 取数据的。真正还缺的是**别的**管线：
   网格的顶点缓冲仍然只能来自 `Mesh`，storage texture 也还不能当材质贴图。
   要做 GPU 蒙皮、GPU 剔除、计算着色器生成的地形，那些口子还得单开。
5. **自定义材质改不了管线状态** —— 钩子只覆盖表面属性，写不了顶点变形、
   改不了光栅化状态和深度测试。这是钩子式设计的明确代价，不是遗漏，
   但要写体积雾、贴花式的深度技巧时会撞上。

###### 顺带修掉的两个真 bug（都是「装了但没生效」）

1. **三级级联渲染出逐字节相同的深度图。** 原来每级各 `write_buffer` 一次
   同一段缓冲、各开一个 pass，而 wgpu 的写入是在**提交的命令之前**统一
   执行的——三个 pass 全读到最后一次写入的值。改用动态偏移，一次写完。
   读回比对确认：修复前三层全等，修复后最小深度 0.73 / 0.55 / 0.52。
2. **地形完全不投影。** 阴影管线是 `cull_mode: Front`（只画背面），
   那只对**闭合网格**成立。地形是单面的，正面朝光，剔掉正面就什么都不剩——
   实测阴影图全是清除值。改成两面都画。

**我之前对 CSM 的「验证」只查了 CPU 端的纹素密度，从没验过 GPU 真的用上了
那些矩阵。** 这正是本文档反复记的那类错误。

##### 8. 脚本 ✅ 已完成

- [x] **模块系统** —— CommonJS 风格的 `require`，不是 ES `import`
      （脚本本身是函数体，且 ES 模块解析是异步的，与「一帧内同步跑完」冲突）。
      源码通过对象属性直接写进各运行时自己的 Context，不拼 JS 去 eval。
- [x] **状态序列化** —— 显式的 `_save()` / `_load(state)`，走 JS 自己的
      `JSON.stringify`。闭包变量存不下来，这是设计而非遗漏。
- [x] **API 覆盖** —— 动画（播放/停止/速度/查询）、粒子（开关/发射率/喷发/计数）、
      音频（播放/停止/音量/音高/循环）。
- [x] **调试支持** —— 挂掉的实例留下**第一条**错误、从实例反查节点与脚本名、
      `revive()` 复活、以及 `eval_in()` 在实例上下文里求值表达式（REPL 式）。
      真正的断点单步调试器 boa 撑不起来（没有 `debugger` 语句、没有调试协议）。

###### 顺带修掉的一个真 bug

**脚本根本没被序列化。** `kscript` 的文档一直写着「因此脚本能随场景存档」，
但 `serialize.rs` 里完全没有 `ScriptSlot` 的处理——存档读回来之后
`script()` 返回 `None`，**任何挂了脚本的场景，存档后脚本全没了**。

###### 两条容易踩的限制（都有测试记着）

- **脚本顶层的 `self` 是个 id 无效的 Node**，不是 null。`self.name` 静默返回
  null、`self.valid` 是 false。要用 `self` 就写在生命周期方法里。
- **闭包变量从外面够不着**，`eval_in` 也读不到。要能查就挂到 `this` 上。

### 三、建议的执行顺序

```
角色控制器（kphysics，3D + 2D）    ← 没有就做不出游戏
   ↓
音频流（kaudio）                   ← 有 BGM 就必须有
   ↓
高度图序列化（kterrain）           ← 做出来了存不下来
   ↓
拾取                               ← 做不了交互
   ↓
剩下的按兴趣调序：
  地形 splat 着色器 / 2D 关节与扫掠 / UI 四个小件 /
  反射探针烘焙 / GPU 粒子
```

前四项的共同点：**都不是"更好看"，是"能不能做"。**
排在后面的那些做完了画面会更好，但没有它们照样能出一个完整的游戏；
没有角色控制器和音频流，出不来。

`uniform_sizes_match_wgsl_layout` 这一条测试拦住过我**三次**（级联、`ibl_params`、
探针参数）。CPU 和 WGSL 的结构体大小对不上是不报错的，只会渲染出垃圾。

### 五、几条明确的取舍

写下来免得将来反复纠结：

1. **不做 ECS。** 场景图路线已定，为局部收益再引入一套实体存储只会多一层
   要同步的状态。Bevy 的 ECS 有 118 k 行，那是它的整个架构，不是可选组件。
2. **不做多后端图形抽象。** wgpu 已经是抽象层了，再套一层没有意义。
3. **UI 布局不自己写。** 接 taffy。自己写 flexbox 是个陷阱 ——
   语义细节极多，而且完全没有引擎特异性。
4. **不做编辑器。** 连带结论：UI 只做 HUD / 菜单 / 调试浮层；
   反射系统失去最后一个正当消费者，已删。
5. **每个第三方引擎关在一个 crate 里。** wgpu→krender、rapier→kphysics
   （2D 和 3D 都在里面）、cpal/symphonia→kaudio、boa→kscript、
   ab_glyph→kfont、taffy→kui。
6. **纯 Rust 工具链。** `cargo build` 不能需要外部工具链 ——
   这是选 rapier 而不是 Jolt 的唯一理由。
7. **性能数字必须有 benches 撑着才写进文档**，而且必须是同一轮里
   和一条不受改动影响的 bench 比出来的比值。
8. **2D 不走节点组件。** 2D 是立即模式精灵，套一层节点组件等于强迫
   2D 游戏用一个它不需要的场景图。

### 六、我看不见的东西

这份文档里所有"完成"都是**测试通过 + 无校验错误 + 关键数值符合预期**，
**不包括画面对不对**。以下这些必须由人看：

- 阴影级联的接缝、贴花的边缘与 z-fighting、金属球在探针里的反射变化
- HDR 环境下的整体曝光、FXAA 是否把文字糊了
- UI 在 DPI ≠ 1 的显示器上的表现（本机没验过）
- 2D 物理的手感（盒子堆得稳不稳、球滚下斜坡对不对）
- 音频的空间感

另外**没有任何真实 `.hdr` 文件被解码过** —— 全部测试用的是程序化生成的
小图，各家工具导出的 RLE 变体能不能解仍然未验。


## 第三部分 · 对象驱动 demo 与脚本引擎

### 一、你的引擎是不是这个架构

**是，而且已经跑起来了。** 对照你画的那张图：

```
Engine Core (Rust)      →  29 个 k* crate：krender / kphysics / kscene / …
JS Binding / FFI        →  kscript::bridge（扁平原生函数 __k.*）
                           kscript::host（把 Scene 整个搬进线程局部，零 unsafe）
JavaScript Runtime      →  kscript::runtime（boa_engine 0.21）
Game Scripts            →  prelude.js 把桥包成 GDScript 手感：self / Node / Vector3
Player / Enemy / …      →  节点上的 ScriptSlot，一个节点一个脚本实例
```

`Scene → Node → Script` 这条链是现成的：`kscene::Node` 上有 `ScriptSlot`
（只存路径，所以能随场景存档），`kscene` 完全不认识 boa；`ScriptRuntime`
每帧 `_process`、每物理子步 `_physics_process`，还带热重载、`_save`/`_load`
存档、`emit` 信号回 Rust、`require` 模块系统、出错自动停用 + 首错留存。

比图上多的：脚本能**当场读写场景、当场打射线**（`raycast` 即时返回），
不是「快照进、命令出」。这一条是 `examples/script_hotreload.rs` 已经在演示的。

### 二、要做 Player / Enemy / Inventory，缺三样

demo 逼出来的三个真实缺口（不是为了写 demo 硬造的需求）：

1. **脚本读不到输入。** 桥里没有任何输入函数。Player 脚本连走路都做不到，
   只能由 Rust 侧代劳——那就不叫脚本驱动了。
2. **脚本生不出节点。** 只有 `queueFree` 删，没有生。敌人刷新、子弹、掉落物
   全都做不了。这是「对象驱动」最核心的一半。
3. **脚本之间说不上话。** 现在只有 `emit`（JS → Rust 单向数值）。
   GDScript 里的 `get_node("Inventory").add_item(...)` 在这儿写不出来，
   Inventory 这种「一个对象持有状态、别人调它的方法」的模式就无从谈起。

结论：这三样都得补，属于**重大修改**，所以有这份计划。

### 三、执行计划

#### 步骤 1 —— 输入进桥（kscript）

沿用 host 现成的「搬进线程局部」手法，`Input` 和 `Scene` 一起 park
（`Input: Default`，两次 memcpy，零 unsafe，与现有三条不变量一致）。

- `host.rs`：`Host` 加 `input: Option<Input>`；`HostGuard::park` 多收一个
  `&mut Input` 与一个 `spare_input`；加 `with_input`。
- `bridge.rs`：`actionPressed / actionJustPressed / actionJustReleased /
  axis / axisVector / mousePosition / mouseDelta / mouseButton(name) /
  mouseButtonJustPressed(name)`。
- `prelude.js`：包成 `Input.pressed("jump")` / `Input.axis("move_x")` /
  `Input.axisVector("move_x","move_z")` / `Input.mouse` 等。

**只暴露 action / axis，不暴露具体键位。** 键位绑定留在 Rust 侧的
`Bindings`——脚本里硬编码 `KeyCode` 会让改键功能永远做不了，
而 kinput 的整套设计就是为了避免这件事。

- 签名变化：`ScriptRuntime::process(scene, input, resources, dt, elapsed)`、
  `physics_process(scene, input, dt, elapsed)`。改 8 处测试调用点 + kapp 2 处。

#### 步骤 2 —— 生成节点：原型注册表（kscript + kapp）

脚本不该认识 `Mesh`、`PbrMaterial`——那会把整个渲染栈拖进 JS 层。
改成**游戏侧注册原型、脚本按名字生成**：

```rust
App::new().with_prototype("Enemy", || {
    Node::new("Enemy").with_mesh(Mesh::cube()).with_script("…/enemy.js")
})
```

```js
const e = spawn("Enemy", new Vector3(x, 0.5, z));   // 返回 Node，立刻可用
```

- `Host` 加 `prototypes: FxHashMap<String, Box<dyn Fn() -> Node>>`
  （随 Host 一起 take/swap，闭包 `'static`）。
- `ScriptRuntime::register_prototype(name, f)`；`App::with_prototype` 转发。
- 桥 `spawn(name, x, y, z)`：取原型 → 设位置 → `scene.add_node`
  （它会就地登记物理索引，所以带碰撞体的原型当帧就进物理世界）→ 返回登记下标。
- 一帧的生成数量设上限（同 `MAX_SIGNALS` 的思路），防写错的脚本把内存吃光。
- 新生成节点若带脚本，下一帧由 `instantiate_pending` 实例化——晚一帧，可接受，
  在文档里写明。

#### 步骤 3 —— 脚本间调用：`node.script`（kscript）

**不加 Rust 桥**——桥的不变量 2 是「借用期间不碰 VM」，
在原生函数里回调 JS 正好违反它。改成纯 JS 侧的实例登记表：

- `runtime` 实例化成功后，把实例对象写进全局 `__instances[nodeId]`
  （`nodeId` 取自 `host.registry`，与桥用的是同一套下标）；实例回收时删掉。
- `prelude.js`：`get script() { return __instances[this._id] ?? null; }`。

于是：

```js
getNode("Inventory").script.add("coin", 1);
target.script.hit(25);
```

零 Rust 代码、零重入风险，正好是「对象驱动」要的那个手感。

#### 步骤 4 —— demo（examples/kengine/demo/）

一个能玩的小竞技场，四类对象各自由脚本驱动：

```
main.rs            场景、键位绑定、原型注册、HUD（kui）
scripts/player.js      读 axis 移动 + 转向；攻击生成子弹；hp / damage()
scripts/enemy.js       追玩家；hit(dmg) 被子弹调用；死亡时 spawn("Coin") 并 emit
scripts/bullet.js      前进 + 命中检测 + 超时自毁；调 enemy.script.hit()
scripts/coin.js        旋转浮动；靠近玩家时调 inventory.script.add()
scripts/inventory.js   纯数据对象：items / add / count；_save + _load 演示存档
scripts/spawner.js     定时 spawn("Enemy")，并持有敌人列表供子弹查询
scripts/camera.js      平滑跟随玩家
```

- HUD 走 `emit` → `ctx.script_events` → kui：血量、金币、击杀数。
- **刻意不碰角色控制器**（`next.md` 里 P0 的那个空洞）：玩家与敌人都用纯变换
  移动 + 距离判定，不依赖 rapier 的 `KinematicCharacterController`。
  demo 因此不会撞在已知缺口上。
- `Cargo.toml` 加 `[[example]] name = "demo"`。

#### 步骤 5 —— 收尾

- kscript 补测试：输入桥、spawn（含无效原型名、上限）、`node.script`
  （含节点已死时返回 null）。
- `cargo fmt` + `cargo clippy` + `cargo test -p kscript`。
- `cargo run --example demo` 实跑确认。

### 五、执行结果

五步全部做完，另外**修掉了两个路上撞见的既有 bug**（都不是这次改动引入的，
但都挡着例子跑起来）：

#### 已完成

| | 东西 | 位置 |
|---|---|---|
| 1 | 输入进桥（action / axis / 鼠标） | `kscript/{host,bridge,runtime}.rs` + `prelude.js` |
| 2 | `spawn` + 原型注册表（每 tick 上限 1024） | 同上 + `App::with_prototype` |
| 3 | `node.script` 脚本间调用（纯 JS 侧登记表） | `runtime.rs` + `prelude.js` |
| 4 | `node.forward`（`lookAt` 的读侧，子弹靠它取方向） | `bridge.rs` + `prelude.js` |
| 5 | demo：7 个脚本 + 200 行 Rust | `examples/kengine/demo/` |
| 6 | 12 条单元测试 + 7 条 demo 集成测试 | `kscript/object_tests.rs`、`tests/demo_scripts.rs` |

#### 路上修掉的两个既有 bug

**一、`App` 内联了整个 `Runtime`，链式构建把主线程栈啃光。**

`App` 是 `.with_xxx(mut self) -> Self` 一路链下来的，而它内联着 `Runtime`
（`Scene` 11.5 KB + `ScriptRuntime` 24 KB + 渲染器…），debug 构建下每一环都在栈上
复制一整份。Windows 主线程只有 1 MB，链上七八个 `with_` 就到顶了——
症状是 `STATUS_STACK_OVERFLOW`，发生在 `resumed` 之前，一行日志都来不及打。
`script_hotreload` 已经中招（在这次改动之前就跑不起来）。

改成 `Option<Box<Runtime>>`，并加了一条 `size_of::<App>() < 1024` 的回归线。

**二、`kapp` 从不注册 `ScriptLoader`，所有脚本都是死的。**

`Node::with_script` 存的是资源路径，运行时每帧拿它去 `request::<Script>`——
但没人往 `ResourceManager` 里装脚本加载器，日志里只有一句
「没有能处理 `js` 的加载器」。挂了脚本的节点于是安安静静什么都不做。

现在 `kapp` 建资源管理器时自动装上（glTF、贴图那些仍由游戏自己注册：
那是游戏的资源，脚本加载器是引擎自己要用的）。

#### 追加：park 每帧连造带拆一整个物理世界

问「为什么每帧都要去 request 脚本」时顺出来的。答案是**并没有**——
已实例化的槽位在三个布尔判断之后就跳过了，每帧真正发生的只是扫一遍
`script_nodes()`，实测 **6~8 ns/节点**（两千个节点约 13 µs，淹在噪声里）。

但量的过程中撞见了真正在烧钱的地方：`HostGuard::park` 里那句

```rust
let real_scene = std::mem::take(spare);   // take = 换上一个 Scene::default()
```

`mem::take` 会**新建一整个 `Scene`（含 rapier 物理世界）**顶替，`Drop` 里换出来
的空壳随后被析构。实测 `Scene::new + drop = 63.7 µs`，而 `kapp` 每帧至少 park
两次（`process` + 物理子步的 `physics_process`）。

这和那段代码自己的注释直接矛盾——注释说「空壳由运行时长期持有并复用」，
`take` 把这个意图破坏了。

改成 `spare: Option<Scene>`，park 时取出空壳顶上、`Drop` 时收回，
稳态下零分配零析构：

| | 每帧固定开销 |
|---|---:|
| 改之前 | **113 µs** |
| 改之后 | **3.2 µs** |

回归保护用的是记号而不是计时（计时断言在 CI 上必闪）：给空壳加一个节点，
被重造的话记号就没了 —— `host::test::the_empty_shell_is_recycled_not_rebuilt`。

#### 追加：`prelude.js` 的内部字段改用私有字段

`self.position.y += dt` 这一行，每写一次要新建一个 `Node` 加一个
`BoundVector3`，而两个类的构造函数原本都在调 `Object.defineProperty`
（为了让 `_id` 不可枚举）。改成 ES 私有字段 `#id`：同样对外不可见
（而且更彻底），但不必每次都走一遍属性描述符流程。

**这一项没有可信的性能数字**——量它的时候机器已经进了热节流，
`empty_callback` 的置信区间跨了 5 倍。留在 `benches/script.rs` 里的
`raw_bridge` 那一档是为它准备的标尺：它绕开整个包装层直接捅桥，
和 `running` 的差值就是包装的价钱，且不受机器状态影响。
**在安静的机器上跑一次才能定论。**

已知的是数量级：`raw_bridge` 那一档测得很稳（334–410 µs / 100 实例），
而 `running` 最乐观也要 4.5 ms —— 包装层占了这条路径九成以上。
真要提脚本吞吐，那里才是下一个靶子。

- `cargo test --workspace`：全绿（新增 19 条）。
- `cargo clippy --all-targets`：本次改动零警告
  （`kui_widgets` 里还有 4 条，是工作区里原本就有的）。
- `cargo run --example demo` 实跑：刷到第 13 波、7 次击杀、3 枚金币、

### 追加：执行引擎补课（异步、信号、变换、树）

对照 GDScript 还缺的几样，这一轮补齐：

| 缺口 | 现在 |
|---|---|
| `await` 永远不回来——boa 的 Promise 任务排进了队列，但没人跑 | 每次回调之后清队列；`wait(秒)` / `nextFrame()` / `setTimeout` / `setInterval`，**游戏时间** |
| `self` 是「当前在跑谁」的全局 getter，`await` 之后指向别人 | `self` 改成工厂参数，绑定在实例自己的节点上 |
| `async _ready()` 里的异常无声消失 | 盯住返回的 Promise，被拒绝时停掉那个脚本；计时器、信号回调同理 |
| 脚本之间只能直接调方法 | `node.connect / disconnect / emitSignal / toSignal`（可 `await`），回调里 `self` 是订阅者 |
| 只有 `rotateY`、`lookAt` | `rotation` / `rotationDegrees`（YXZ，同 Godot）、`quaternion`、`rotateX/Z`、`rotate(轴, 角)` 本地 / `rotateGlobal` 父空间、`right` / `up`、可写的 `globalPosition`、`toGlobal / toLocal` |
| 只能按名字全局找节点 | `parent` / `children` / `findChild` / 路径 `"../Door/Handle"`、`"/Level/Door"` / `reparent(保持世界位置)` / `equals` |
| `globalPosition`、`forward` 读的是上一次 `scene.update()` 的缓存——当帧改了读不到 | 现算 |
| 报错 `unknown at :189:22` | `enemy.js:4:14`，行号就是文件行号 |
| `print({a:1})` 打出 `[object Object]` | 展开；另有 `console.log/info/debug/warn/error/assert/time`，`ScriptRuntime::take_console()` 取走 |
| 热重载丢状态 | 有 `_save` / `_load` 的脚本带着状态换代码 |
| 没有数学工具 | `Quaternion`（slerp、fromTo、toEuler）、`Mathf`（wrap、lerpAngle、damp、smoothstep……）、可设种子的 `RandomNumberGenerator` 与全局 `randf/randi/seed`、Vector3 的 `angleTo/rotated/slide/reflect/moveToward/limitLength…` |

**性能**：每次回调后清 Promise 队列，boa 自带的执行器空跑一次也要搭一整套 future 组，
空回调因此慢了四成。任务队列包了一层计数，空时直接跳过，开销收回到 5% 以内。
顺带把 `self.position` 的代理对象缓存在 Node 上（`self` 现在是常驻对象）：
`self.position.y += dt` 从 857 µs / 100 实例降到 441 µs，和直接捅桥（160 µs）的差距从 5.4 倍缩到 2.8 倍。
剩下的主要是 `+=` 那一次读——它本来就要多过一次桥。

**一个 boa 的坑**：前一个脚本里定义的函数看不见后一个脚本的顶层 `class` / `const`

   写的是 `det = dir.dot(edge1.cross(edge2))`，标准算法要的是

   一个把该命中的也判成不命中的 bug，天然更容易蒙对「不该命中」的用例。

   `kmesh` 89 项测试全绿。顺手给一直没有测试的 `Scene::pick` 补了三条：

### 顺带修掉的真 bug

1. **点光、聚光的影子按方向光算。** 阴影子系统只有级联，点光的影子成了「从它 −Z 方向打来的平行光」。god rays 例子的光柱全错才暴露出来。
2. **FBX 蒙皮一播动画人就炸开。** Mixamo 导出的 Cluster `Transform` 写的是 `TransformLink` 的逆，照规范用会让绑定姿态平移两倍。改成和 three.js 一样只认 `TransformLink` + 网格自己的全局变换，加了回归测试。
3. **流式音频 seek 只重建解码器、不回绕读包器**，而且解码线程读到文件尾就退出——循环播放的 BGM 放完一遍便没了声音。改成容器级精确 seek + 丢掉目标帧前的样本，线程在文件尾等待而不退出。
4. **纯色背景被色调映射压暗。** three.js 的 `scene.background` 是清屏色不过色调映射；这边背景和物体在同一张 HDR 图里，ACES 下 `0x111111` 成了纯黑。改成对纯色背景反算色调映射与曝光（六种算子都能逆）。
5. **每帧新建贴图会让显存只涨不落。** 渲染器按贴图 id 缓存、从不回收；Lottie 每帧一张新图就是无界增长。加了 `Texture::with_pixels`（同 id 换版本、原地重写）。
6. **Windows 主线程栈溢出。** boa 解析 JS 极吃栈（三层嵌套调用七八百 KB），1 MB 的主线程顶不住，`physics_character` 一启动就 `STATUS_STACK_OVERFLOW`——它根本没用脚本，只因为 kapp 启动时总会建脚本运行时。改成场景里有脚本才建，并给本仓库的可执行文件开 8 MB 栈（根目录 `build.rs`）。
7. **UI 四连**：面板成了角落里一个小药丸（它被当成第一行里的一个空控件来排）；文字行高吃了按钮的 30 像素；主题把 sRGB 的数当线性用，深色面板上屏是中灰；字形按逻辑像素光栅化再按 DPI 放大，150% 缩放下字发虚发胖。四处都修了。
8. **截图里一直没有 UI。** 截图拷的是后处理链，UI 画在那之后——所以前面三条 UI 问题在所有截图里都看不见。改成拷交换链。

### 脚本引擎（kscript）

`await` 以前永远不回来——boa 的 Promise 任务排进了队列但没人跑。补了游戏时间的
`wait` / `nextFrame` / `setTimeout`、信号（`connect` / `emitSignal` / `toSignal`）、
`console`、旋转与节点树 API、四元数和数学工具；`self` 改成工厂参数，`await` 之后不再
指向别人；报错带文件名行号；热重载带状态。细节见第三部分末尾的「追加」。
性能上，任务队列包了一层计数（空时跳过），`self.position` 的代理缓存在 Node 上，
最常见的 `self.position.y += dt` 快了一倍。

### 教训

- **截图要截到用户看到的那一层。** 截图工具漏了 UI，于是 UI 的每个毛病都「通过了视觉检查」。
- **「测试全绿」在 GPU 代码上什么都不保证**，这一轮又证实了三次（影子、背景色、截图）。和参考图逐张比才抓出来。
- **一个子系统的问题常常藏在没人想到的入口。** 栈溢出不是脚本例子触发的，而是一个不用脚本的物理例子——因为初始化路径对所有程序都一样。
- **颜色空间要在 API 上写明**（`srgb(0x……)`），不然「看起来对的数」会被当成另一种空间用。


## 第六部分 · 先能量，再补洞（2026-10）

> 执行 2026-10-03 那一轮迭代方案（原文见[附录](#附录--2026-10-03-那一轮迭代方案原文)）。每项的结果和数字在它的「进度」表里，这里记过程里值得记住的事。

### 做了什么

- **剖析器**：`klog::profile!` / `Sequence`（关着时只读一个原子布尔）；GPU 时间戳三块回读缓冲轮转、从不等待；kapp F3 面板。量出来的第一件事：`physics_character` 一帧 5.7 ms 里渲染器 1.9 ms、其中聚簇 0.8 ms。
- **无头渲染器** `Renderer::headless`：交换链变成可选，屏幕帧画到一张离屏纹理。顺带解锁了渲染器基准和截图回归测试——以前 benches/README 里写着「批处理量不了，headless 起不来」。
- **剔除**：257 → 85 ns / 节点。三刀：逐节点 `Vec` 换迭代器；可见数多时先按节点池顺序排序（BVH 顺序对节点池近乎随机，2 万个 720 字节的节点每个都是缓存缺失）；渲染器跨帧复用绘制项分配（借着场景的 `Vec` 存不进 `self`，靠「空 `Vec` 的 `into_iter().map().collect()` 原地复用分配」换生命周期）。
- **脏标记**：`transform` 是公开字段、谁都能直接写，没法在写入口标脏，于是比对上一次的局部变换。静态场景快一倍；离 30 ns 的目标还差一截，剩下的是每帧重建组件索引要碰整个节点。
- **资源回收**、**管线缓存**、**锁定光标**、**补间**（脚本 `await self.tween(...)`）、**覆盖层相机**、**多光源阴影**、**例子级截图回归**、**拆 `render_frame`**，见进度表。

### 教训

- **先 A/B，再下结论。** 脏标记第一次单跑，「世界变换」那一段反而从 1.08 ms 涨到 1.38 ms——看起来是负优化。同一进程里交替跑带 / 不带脏标记，才看清整体是 2.9 → 1.6 ms，单次数字的波动比改动本身还大。
- **截图测试的场景本身也会骗人。** 第一版 `shadow_cube` 截出来没有影子——不是渲染器坏了，是太阳在相机身后、影子全落在方块背面；聚光灯的角度参数是**度**，传了弧度，光锥小到看不见。基准图生成之后必须人眼看一遍，不然等于把错误画面钉成了「正确答案」。验收时故意关掉阴影采样，恰好两个带阴影的场景失败，才算证明它真能抓东西。
- **驱动有自己的缓存。** 管线缓存在本机测不出差别：NVIDIA 驱动自己的着色器缓存一直是热的。这类优化只在「驱动缓存被清」时生效，量不出来就照实写量不出来。
- **「可复现」要堵三个口子。** 固定帧间隔之后 `demo` 的截图仍然时对时错：脚本里的 `Math.random` 是一个口子（加 `KENGINE_SEED`），资源在后台线程异步加载是另一个——同一份脚本这次第 2 帧就绪、下次第 3 帧，刷怪时机就整体错开一帧（固定步长模式下每帧开头等在途加载做完）。第三个是 GPU 本身：同一画面最多一两个像素差一级，靠分块比对容忍。
- **拆大函数时顺手量一下，比拆本身收获大。** `render_frame` 拆成二十来个小方法之后，剖析面板头一次能把「剔除」和「收集绘制项」分开看，才发现后者每个物体 860 ns，大头是按名字查材质参数——同一份材质一千个物体各查一遍。每帧每份材质只解析一次，那一段快了 2.5 倍。
- **例子里的老 bug 是截图才看得见的。** `first_person_view_model` 的地面一直是 1 米见方（`Mesh::plane` 的参数是贴图平铺次数，不是尺寸），改成两台相机时截图才发现。

## 第七部分 · kcomponents 与海洋演示（2026-10）

对着一个商业海洋演示的功能清单（FFT 波浪、JONSWAP、三级联、无限水面 LOD、多层泡沫、焦散、水下、浮力、程序化天空、八套预设、画质档位），
用 kengine **从头实现**——算法是公开的（Tessendorf 的 FFT 海浪、JONSWAP 谱、Mitsuyasu 方向分布、单次散射大气），代码、界面、场景资源都是自己的。
可复用的部分拆进新 crate `kcomponents`，演示在 `examples/kengine/ocean/`。

### 做法上的几个取舍

- **FFT 在 CPU 上**：引擎还不能把计算着色器的结果直接当贴图（ROADMAP 里列着的缺口），所以三个级联在 CPU 上做，三条线程并行，
  结果编码进一张六层 RGBA8 纹理数组。高度拆成两个字节存 16 位——两个字节各自双线性插值再合起来仍然正确，因为合成是线性的。
- **网格是以相机为圆心的极坐标网格**：圈半径等比增长，屏幕上三角形大小大致不变，一张网格铺到 40 公里外，没有 LOD 接缝要处理。
  波浪按世界坐标采样，网格跟着相机走浪不跟着走。
- **材质参数只有四个 vec4**：水色、雾色、太阳 / 天空辐射、太阳方向放进一张 16×1 的「调色板」贴图。
- **一套大气模型三处用**：天穹逐像素算，CPU 上同一份代码烘环境光（海面反射、船身 IBL）和算太阳颜色，三处对得上。

### 顺带修掉的真 bug

- **`add_force` 永远叠加**（kphysics，2D 和 3D 都有）。文档写着「只在当前这一步有效，步进后自动清零」，但 rapier 的力是持续的、引擎从来没清。
  每个定长步给船加一次浮力，几秒后船被推上天——这个 bug 之前没暴露，是因为整个引擎里没有一处每帧调 `add_force` 的代码。现在每步之后清零，加了测试。
- **`first_person_view_model` 的地面只有 1 米见方**（上一部分记过）。

### 海岛场景（`water_island`）

用 `assets/water/` 里的模型和贴图（荷兰帆船、岛、礁石、浮标、鱼、海草、全景天空、沙子 / 泡沫贴图）搭的场景，
布局照着参考截图摆。资源包里那个编译后的 JS 没有看、也没有移植——只用了模型和贴图。为它给 kcomponents 补了：

- **全景天空**（`Panorama`）：天穹贴照片，环境光由同一张图烘出来，太阳方向取图里最亮的那一块。
- **泡沫贴图**（`Ocean::set_foam_texture`）。
- **水线横穿画面**：水下后处理逐像素判断近平面上那一点在水面哪一侧，镜头半截在水里时画面一分为二。
- **能量倍数**（`SpectrumParams::energy`）：「好看的海」不等于「15 m/s 风吹三百公里的真实海况」。

几个只有截图才看得出来的问题：

- **棕榈树只剩树干**：叶子是半透明混合，不写深度，而海面也在半透明那一趟、画得比它们晚，水面把叶子盖掉了。
  叶子、海草改成镂空（alpha 测试 + 不透明）。第一次只改了节点的主材质——一个 glTF 节点挂了树干 + 叶子两个子网格时会拆成子节点，
  不在实例化的对照表里，得遍历整棵子树。
- **岛的「Plane」是岛本身的沙地**，顶只比原点高 0.35 米，正好卡在海平面上，水面会漫过沙滩：整体抬 0.55 米。
- **从水下看浪的背面白成一片**：法线翻过来朝着相机、掠射角下菲涅耳接近 1，引擎照常加天空反射。用遮蔽当标记让光照钩子跳过。
  「从下面看」也不能拿相机高度和这一点的高度比，相机在浪谷里时远处比它低的浪面照样是背面。

第二轮对着参考图改的五处：

- **浪漫上岛**：加了水深图（`DepthMap`，从岛的顶点烘出来），浅水里浪高打折（`shoal_factor`，CPU 和着色器同一条曲线，
  浮力看到的浪和画出来的是同一个），浅滩上画沿等深线往岸边推的拍岸白线。
- **浮力**：探针从船底挪到船体中间高度、各管一根水柱——放在船底是倒立摆，浮标会翻过来漂着。
  阻尼改按**相对于水**的速度（水速由上一步位移的差分得来），不然阻尼把船钉住、浪头直接漫过船舷。
  调试显示改成绿球（泡得越深越大）+ 黄色力箭头。
- **泡沫**：顺风拉长的花纹、只在花纹亮处留白；衰减从 0.8 改到 0.6/秒。这个场景把频谱能量打了五折，
  雅可比离 1 更近，阈值才需要随风速略抬——和上面「不该跟着风速大涨」不矛盾，是同一个白浪量在补偿能量缩放。
- **水下透射**：雾色按视线方向分级（朝上透亮、平视深蓝、朝下更暗），加了沿视线步进、按阳光投到水面采样的光柱。
- **远处渐暗**：海面雾改成指数平方、离相机 40 米起算；天穹（程序化和全景都有）贴着海平线加一道灰蓝雾带，
  海面雾用同一个颜色，海天接缝不断层。

第三轮（「远处太白、浪和泡沫分不开、没有波光、透射不对、云不动」）：

- **远处太白**：雾色取地平线天色却又提亮、去饱和，远海成了一片白。改成压暗的灰蓝、从 150 米起算，天穹雾带也只去饱和不提亮。
- **浪和泡沫**：浪是蓝色的明暗起伏，泡沫是挂在浪尖上的一缕缕白线。泡沫贴图换成镂空花边那张（foam2），
  用「覆盖率当阈值切纹理」——刚翻卷时只剩最亮的几条细丝，翻得越厉害越满；纹理沿浪峰（横风）拉长，半透明、边缘软。
  最细一级涟漪不再出白浪（大风时处处翻卷，满海碎点）。加一股顺风的涌浪，浪峰连成长长一道，能量回到 0.85。
- **波光粼粼**：FFT 最细一级也有几十厘米，太阳倒影是一大片糊的。光照钩子里叠一层随时间抖动的碎微法线配极窄高光。
- **透射**：浅滩透底改成随水深指数变淡，没有一圈硬边；浪尖透光按「高出平均海面多少（相对浪高）」算，只是一层淡淡的青绿。
- **水下**：深海蓝、光柱淡。
- **云**：默认风速 12 → 30 m/s，云的噪声随时间沿竖轴慢慢演化，不只是整体平移。

第四轮（「只有浪尖才有泡沫，不是乱搞」）：俯视时满海都是碎白点。原因是白浪取了风浪那一级（3–19 米）的雅可比——
大风时这些短浪到处都在「折叠」。改成只看最大那一级（19 米以上，含主浪）的雅可比、模糊四邻点，再乘一个「在浪峰上」
（这一点大浪高度高出平均海面）的门限：浪谷里不会有白浪，白浪是挂在少数几道大浪浪尖上的一整片。
大浪的雅可比很少跌得很深，阈值相应放到 0.84–0.99。闪光的微法线抖动从 0.5 收到 0.14，只聚在太阳倒影那一条上。

第五轮，对着产品说明补齐缺的四样：

- **屏幕空间反射**：在环境光钩子里沿反射方向世界空间步进 28 步（步长等比放大）、投到屏幕和深度缓冲比，打中后二分细化四次。
  深度缓冲里只有不透明物体（水面自己在半透明那一趟），倒影里自然是船、岛、礁石；没打中的地方仍是天空环境图。
  贴屏幕边、走得远的命中淡出。用 `WaterLook::reflections` 调强度。
- **三层泡沫**（`FoamLayers`）：白浪（大浪浪尖破碎）、表面薄沫（泡沫图里慢慢衰减的残余，看得更宽、不要求在浪峰上、顺风拉条）、
  岸边（岸线接触、拍岸浪、物体周围、尾迹）。各有纹理（`set_foam_textures`，借基础色 / 自发光 / 遮蔽三个海面用不上的贴图槽）、
  颜色、覆盖量、平铺尺度（调色板 11–14）。三层按「1 − 都没盖住」合成，颜色按量加权。海岛用资源包里的三张泡沫图各管一层。
- **单点浮力**（`Buoyancy::point`）：中心查一次海面，再用扶正力矩把物体转向水面法线。浮标、木箱、木桶用它；船仍是多点。
- **尾迹发生器**（`WakeMap::emit`）：尾迹图除了白沫再存一张波动方程网格（256 格 × 320 米）。物体把水往下压，压出的凹坑以波传开；
  波速（2.4 米/秒）比船慢，船压出来的波来不及跑到前面，在身后叠成 V 字。几个物体的波直接叠加、干涉。顶点阶段叠高度，
  片元阶段差分出坡度，坡陡处翻白沫。CPU 的 `Ocean::sample` 也加上尾迹高度，漂浮物会被别人的尾迹推着晃。
  一开始波速 5.5 米/秒、比船快，波全跑到前面散掉，尾浪只有 2–5 厘米高，看不见。

性能：屏幕空间反射和尾迹让 release 从 136 帧降到 97 帧；debug 下（kcomponents、krender、kscene、kanim 开了 opt-level 3）78 帧。

第六轮（「远处的浪不对，好像多普勒效应」）——其实是两个毛病叠在一起：

- **走样（摩尔纹）**：掠射角下远处一个像素沿视线方向盖住好几米海面，风浪那一级的纹素只有 0.9 米（高画质 128²：112 米 / 128），采样出来是压扁、发颤的假花纹。
  原来按「离相机多远」淡出各级，和像素多大没关系——相机低、看得平时远远不够。改成按像素在海面上的覆盖（`dpdx`/`dpdy` 取长轴）
  和每级纹素之比淡出（1.5–6 倍之间），退掉的起伏照旧变成粗糙度：远处是大涌浪加一片柔和光泽。闪光也按粗估的像素大小淡出。
- **远处一道道暗纹**：逐像素拿「法线背着相机」判断「从水下看」，掠射角下远处浪的背坡全被当成水下，画成暗色、没有反射。
  改成整帧一个答案——CPU 按相机处的浪高判断相机在不在水里，写进调色板第 15 格；法线背着相机的点往视线方向掰一点。

### 教训

- **单次散射的地平线是黄的。** 沿贴地视线一路积到大气顶（几百公里），蓝光全被散射掉；真实天空靠多次散射把地平线补成白色。
  把视线积分截到 80 公里是多次散射最便宜的替身——数字上地平线从 (1.03, 0.94, 0.47) 变成 (1.13, 1.22, 1.11)。
- **WGSL 里变量名会遮住内建函数。** `let length = ...` 之后同一作用域里的 `length(p)` 就是对一个 f32 调用——三个着色器各踩了一次
  （`length`、`step`、`distance`）。着色器测试（`validate_material_hook` / naga 解析）第一时间抓住了它们。
- **泡沫阈值不该跟着风速大涨。** 风大了浪更陡，雅可比自然更容易跌破阈值，白浪变多是物理自己算出来的；再把阈值往上调就是双重计算，风暴预设整片海全白。

## 第八部分 · three.js webgpu 第二批（54 个）与引擎补课（2026-10）

three.js 的 `webgpu_reflection*` … `webgpu_volume_cloud` 共 54 个例子，全部移植到 `examples/kengine/new/`，每个都对着
`examples/threejs/screenshots/` 里的参考图看过。原则不变：例子做不出来就补引擎，补不了的写进例子文档的「和原版的差别」。

### 引擎新增

- **渲染**
  - 存储纹理直接当材质贴图（`StorageTexture::texture()`，共享视图表，不读回）；`StorageFormat::Rgba16Float`（可过滤）。
  - **三维纹理**：`Texture::volume` + 材质的 `custom_texture_3d` 槽（层间三线性插值）。
  - `BlendMode::Additive`：半透明管线改成预乘混合，叠加只是着色器输出 (rgb·a, 0)，不多编管线。
  - `Material::with_depth_write`（半透明也写深度，单独一趟可写深度的 pass）；`with_blended_shadows`（半透明也投影，默认关）。
  - 第五个钩子 `material_output`（three.js 的 `outputNode`）；`Surface.front_facing`、`Surface.transmitted`（不被阴影挡的光）；
    顶点钩子能写 `uv` / `uv1` / `color`、读 `tangent`。
  - 参数槽 8 → 16（程序化木纹 7 个 + 物理材质 5 个）。
  - mip 链 + 各向异性过滤（以前材质贴图没有 mip）；`Light::shadow_radius`；镂空材质的阴影也镂空；`ShadowMaterial`；离屏相机视图当材质贴图。
  - `PostSettings::render_scale` + `Upscaling::{Bilinear, Fsr1, Taau}`：低分辨率渲染，FSR1（EASU + RCAS）或时间性放大到窗口。
  - `krender::composed_material_shader`（看钩子拼进去之后的完整 WGSL）。
- **着色器**：`kshader::noise`（MaterialX 噪声，和 TSL 的 `mx_*` 同一套哈希——程序化地形和参考图**连地形形状都一样**）、
  `tsl_tri_noise3d`；`kshader::glsl::{to_wgsl, shadertoy_to_wgsl}`（naga 的 GLSL 前端，ShaderToy 代码原样能跑）；`Shader::used_bindings`。
- **计算**：`create_pipeline_entry`（一份源码多个核）；`dispatch_with` 只绑这个入口用到的绑定。
- **几何 / 材质**：`Mesh::plane_subdivided`、`rounded_box_sized`、`with_bounds`（顶点钩子挪出原包围盒不被剔除）、`MeshBvh`；
  `kpbr::wood::WoodMaterial`（`WoodNodeMaterial` 逐函数移植，十种预设）。
- **纹理**：KTX2 的 `layerCount`（以前数组只解第 0 层）。
- **视频**：新 crate `kvideo`——MP4 拆包（`mp4`）+ OpenH264 解码（源码随 crate 编译，不要系统 ffmpeg），`VideoPlayer::advance` 出 RGBA 帧。

### 顺带修掉的真 bug

- **球的 UV 是镜像的。** `Mesh::sphere` 的 u = 0 在 +X、转向 +Z，从外面看等距柱状投影的地图东西颠倒。地球例子和参考图对不上经度才发现。
- **白底 + Neutral 色调映射整个画面糊成一片。** 纯色背景要反算色调映射；Neutral 只在无穷远处到 1，白色反算出上限 256，进 Bloom 就是一片雾。
  现在取「显示出来是同一个 8 位色阶」的最小值（约 15）。
- **聚光的体积光糊满整个画面**：阴影图视锥外一律当「照到」。聚光现在锥外是 0、锥边软化。
- **半透明物体从来不投影**（阴影 pass 只画不透明批次）。
- **材质缓存键在克隆分叉后会撞**（同 id、同版本号 + 1）：两份不同参数的材质被渲染器当成一份。改成全局计数器。
- OpenH264 默认每次解码后强制刷新，带 B 帧的 Main 档视频第 9 帧之后就全坏了。

### 教训

- **参考截图是最好的测试。** 地形形状、地球经度、晕影的位置、TSL `a.step(b)` 的参数顺序——这些全是对着参考图比出来的，单测发现不了。
  `step` 的顺序两个例子给出了相反的暗示，最后是半色调例子的截图定的。
- **「对的」常量组合起来可以错。** Neutral 曲线本身没错，背景反算本身也没错，两者碰上白背景才出事。
- **H: 盘在重编译时掉过两次**（一次满盘，一次 143 GB 余量时）：错误是 `os error 433` / `STATUS_IN_PAGE_ERROR`，不是代码问题。之后用 `-j 4` 编。
- **一份模块里的「顺手」不顺手**：顶点钩子读 `globals` 的话阴影管线建不出来（同号绑定），只能退回普通阴影——公告板类的例子都要记得这点。

### 零、结论先说

引擎功能面已经很宽（2734 项测试、164 个例子、30 多种导入格式），代码卫生也好
（全工作区 clippy 只有 25 条、几乎全是风格类）。现在最值得投入的不是再加一个渲染特性，而是三件事：

1. **先能量。** 引擎**没有任何帧耗时数据**——没有 CPU 分段计时、没有 GPU 时间戳、
   连垂直同步都关不掉，所以没人知道一帧里时间花在哪。所有性能工作都卡在这一步。
2. **堵两个长期运行才会暴露的洞**：GPU 资源**只进不出**（贴图、网格、管线、绑定组都没有回收），
   和**一帧只有一盏灯能投影**。前者是换关卡几次就爆显存，后者是任何多光源场景都不对。
3. **把「测试全绿、画面不对」这类 bug 变成能自动抓的。** 这一年记录在案的真 bug 里，
   大半是 GPU 侧的「装了没生效」，只有截图和人眼抓得到。截图对比已经手工做了几百次，该做成测试了。

之后再按游戏需要补功能：鼠标锁定、补间、覆盖层相机、导航寻路、手柄。

### 一、依据（2026-10-03 实测）

#### 性能

| 测量 | 结果 | 怎么量的 |
|---|---|---|
| 场景更新 | 118 ns / 节点（2 万节点 2.36 ms） | `cargo bench --bench scene`，`scene_update/flat/20000` |
| 视锥剔除（部分可见） | **257 ns / 节点**（2 万节点 5.15 ms） | `culling/partial/20000` |
| 视锥剔除（全可见） | 160 ns / 节点 | `culling/all_visible/5000` |
| 稳态帧 | 被垂直同步锁死（60 / 100 Hz 各一次），**测不出余量** | release 构建，截第 60 帧与第 360 帧的耗时差 |
| 冷启动 | 第 60 帧在 **4.1 s**（驱动着色器缓存冷） vs 热启动 2.2 s | 同上，连跑两次 |
| 进程启动到首帧 | ≈ 1.0 s | 日志时间戳 |
| `self.position.y += dt`（脚本） | 4.4 µs / 实例（直接捅桥 1.6 µs） | `cargo bench --bench script` |

剔除慢的原因已经定位：BVH 本身没问题，`Scene::cull` 给**每个可见节点**都
`render_items_for_node` 新建一个 `Vec<RenderItem>` 再 `flat_map` 收集；阴影的每一级 / 每一面又各剔一遍。
场景更新慢的原因：**每帧重算全部世界变换**，没有脏标记。

#### 资源生命周期

`krender` 里 `gpu_textures`、`meshes`、`material_pipelines`、`double_sided_pipelines`、
`material_modules`、`material_bind_groups` 六张缓存表，**只有显式 `remove_mesh` 和贴图尺寸变化
两处会删**。场景切换、模型卸载之后它们留在显存里。一个反复进出关卡的游戏，显存只涨不落。

#### 结构

| | |
|---|---|
| `krender/src/lib.rs` | 6736 行，`render_frame` 一个函数约 1800 行 |
| `kscene` | 1.24 万行（场景图 + 物理 / 音频同步 + 流式加载 + 序列化 + 若干接线） |
| 测试密度最低（测试数 / 千行） | ktask 5、kimport 8、kgltf 9、kcore 10、kapp 11、krender 11 |

#### 功能缺口（全仓库确认没有）

多光源阴影、遮挡剔除、手柄、鼠标锁定、补间系统、导航网格 / 寻路、本地化、根运动、
动画重定向、WebAssembly 目标、管线缓存。（另有 ROADMAP 里列着的覆盖层相机、
顶点钩子进阴影、文字整形等。）`gilrs`（手柄）和 `rustybuzz`（整形）本机 cargo 缓存里没有，要联网加依赖。

### 二、方案

工作量：S ≈ 一两天，M ≈ 一周内，L ≈ 一两周。每项都写了**验收标准**——做到才算完。

#### 阶段 A · 先能量（S + S + M）

##### A1 · 帧剖析器

**问题**：没有帧耗时数据，优化无从下手；性能回归只能靠 bench，而 bench 覆盖不到渲染器。

**方案**：
- CPU 侧：`klog` 加一个零依赖的作用域计时（`let _t = profile!("cull");`），按帧汇总成
  「阶段 → 毫秒」表；关闭时编译成空。kapp 每个 `Stage`、krender 每个 pass 各插一个。
- GPU 侧：adapter 支持 `TIMESTAMP_QUERY` 时，每个 pass 前后写时间戳，异步读回（落后两三帧没关系）。
- 调试面板（已有 `DebugDraw` 开关）加一页：CPU / GPU 分段柱状图 + 最近 120 帧折线。
- `ScriptRuntime` 里每个脚本实例的耗时也记下来——游戏里「哪个脚本慢」是最常问的问题。

**验收**：任何例子按一个键就能看到「这一帧 GPU 里阴影 x ms、SSAO y ms、后处理链各 effect 各几 ms；
CPU 里剔除、合批、上传、脚本各几 ms」，读数与 RenderDoc / Tracy 同量级。

##### A2 · 关掉垂直同步

`KENGINE_PRESENT=immediate|mailbox|fifo` 环境变量 + `App::with_present_mode`。
**验收**：release 下例子跑出不锁帧的帧率，A1 的数字才有意义。

##### A3 · 渲染器 CPU 基准

`benches/render.rs`：无头设备、离屏目标（`FrameMode::Capture` 那条路已经不碰交换链），
量 1k / 10k / 50k 个物体时 `render` 的 CPU 时间（剔除 + 合批 + 上传 + 编码命令）。
按项目规矩，配一条不受改动影响的对照 bench，报比值不报绝对数。

**验收**：B 阶段每一项都能在这组 bench 上看到前后比值。

#### 阶段 B · 性能与资源（M + M + S + S）

##### B1 · GPU 资源回收

**方案**：每张缓存表的值带一个 `last_used: u64`（帧号），用到就更新；每帧末尾扫一小段
（摊开扫，不一次扫全表），**连续 N 帧（默认 300）没用到就释放**。被释放的再用到时自然重传——
`Resource` 句柄还在，数据在 CPU 侧。绑定组随它引用的贴图一起删。`RenderStats` 加上各表的条目数与估算显存。

**验收**：加一条测试 / 例子：来回加载卸载同一个大场景 50 次，各表条目数和显存估算回到基线；
正常场景下没有「刚删又传」的抖动（被删的确实是 N 帧都没用过的）。

##### B2 · 剔除与提交去掉逐节点分配

**方案**：`Scene::cull_into(&mut Vec<RenderItem>)` 复用调用方的缓冲；`render_items_for_node`
改成往里 `push` 而不是返回 `Vec`；渲染器跨帧保留这块缓冲。阴影：主视锥剔一次之后，
各级联 / 各面在 BVH 上各查一次索引（便宜），共享同一份 `RenderItem` 数据而不是重建。

**验收**：`culling/partial/20000` 从 257 ns / 节点降到 **≤ 100 ns**；A3 里 10k 物体带三级级联的帧准备时间下降可见。

##### B3 · 管线缓存（冷启动）

**方案**：Vulkan 后端用 wgpu 的 `PipelineCache`，序列化到用户缓存目录，下次启动带上；
加载阶段把场景里已知的材质管线**预编译**掉，而不是第一次画到才编。

**验收**：清掉驱动缓存后的冷启动，第 60 帧时间从 4.1 s 接近热启动的 2.2 s；首次出现新材质时不再卡一帧。

##### B4 · 场景更新加脏标记

**方案**：变换写入时标脏（`transform_mut` / 物理同步 / 动画写回都走同一个口子），
`Scene::update` 跳过干净的子树。注意：动画、物理驱动的节点每帧都脏，收益主要在静态场景。

**验收**：`scene_update/flat/20000` 在 90% 节点静止时降到 **≤ 30 ns / 节点**；全动态时不慢于现在。

#### 阶段 C · 防「测试全绿、画面不对」（M）

##### C1 · 截图回归测试

**问题**：记录在案的真 bug——点光影子按方向光算、三级级联同一个矩阵、地形不投影、
背景被色调映射压暗、截图里没有 UI、UI 主题颜色空间错——测试全是绿的。抓到它们靠的是截图和参考图对比，
而这件事这一年手工做了几百次。

**方案**：`tests/screenshots.rs`（默认 `#[ignore]`，CI 上有 GPU 时跑）：挑二三十个覆盖面广的例子，
固定种子、固定时间步、固定窗口尺寸，截第 N 帧，和 `tests/golden/*.png` 按**感知差**（SSIM 或分块均值差）比；
超阈值时把差异图写出来。`cargo test -- --ignored --exact screenshots::update` 一键刷新基准图。
需要的前置：例子支持「固定时间步」环境变量（物理、动画、脚本的时间都从它来）。

**验收**：故意改坏一处（例如把阴影偏移改反），对应例子的截图测试失败并给出差异图；不改时稳定通过（同机连跑 10 次不闪）。

|---|---|---|---|

### 三、建议顺序

```
A2 关垂直同步（S）─┐
A1 剖析器（M）────┼─→ B2 剔除去分配（M）─→ B4 脏标记（S）
A3 渲染器基准（S）─┘        │
                            ├─→ B1 资源回收（M）      ← 长期运行必爆，优先
                            └─→ B3 管线缓存（S）
C1 截图回归（M）  ← 和 A 并行，越早越好：后面每一项都靠它兜底
   ↓
D2 鼠标锁定（S）→ D3 补间（S–M）→ D4 覆盖层相机（M）→ D1 多光源阴影（L）
   ↓
E1 拆 render_frame（有了 A1 + C1 才做）
   ↓
D5 导航 / D6 手柄 / D7–D9 按项目需要挑
```

**第一个里程碑**（A + C1 + B1 + B2）做完时应该能回答：「一帧时间花在哪」「换关卡显存回不回得来」
「改坏了渲染能不能自动发现」——这三个问题现在都答不上。

### 四、不做的（重申）

不做 ECS、编辑器、多图形后端抽象、自写布局，第三方库各关在一个 crate 里，纯 Rust 工具链——
见 ROADMAP「定下来的取舍」。这份方案里的每一项都不违背它们：剖析器、截图回归、导航、补间全是零依赖自写；
需要联网加依赖的只有手柄（gilrs）和文字整形（rustybuzz），都是纯 Rust crate。

### 五、风险

| 风险 | 对策 |
|---|---|
| GPU 时间戳在部分后端 / 集显上不可用 | 不可用时面板只显示 CPU 一栏，不报错 |
| 截图回归在不同显卡上像素不一致 | 按感知差比、阈值留余量；基准图按机器分目录，CI 只比 CI 机器自己的 |
| 资源回收的「刚删又传」抖动 | 阈值按帧数而不是时间；同一资源反复被删重传时记日志，必要时让它常驻 |
| 多光源阴影的显存与带宽 | 预算可配、按影响排序，默认值保守；剖析器先上，看清代价再定默认 |
| 拆 `render_frame` 引入回归 | 必须在剖析器与截图回归之后做，一次只搬一个 pass |

> 动画系统（Animation） — 骨骼动画、蒙皮、状态机、动画混合（blend tree）、IK、Morph Target。
>
> 音频系统（Audio） — 音效播放、3D 空间音频、混音、音频流。常见底层如 FMOD、Wwise、OpenAL。
>
> 输入系统（Input） — 键鼠的事件采集与映射。
>
> 脚本/逻辑系统（Scripting） — 游戏逻辑层，如js脚本语言的集成，提供游戏对象行为定义和事件处理。
>
> 场景管理（Scene / Scene Graph） — 场景树、实体组织、空间划分（八叉树、BVH）、可见性剔除。
>
> 资源管理（Asset / Resource Management） — 资源加载、序列化、打包、内存管理、异步流式加载。
>
>
> 多任务执行：
>
> 底层执行器：多线程任务池
> ktask 提供任务池（基于 async-executor + 类似 work-stealing 的调度），每个"就绪" System 被包装成一个 async task 丢进线程池，线程从队列里认领任务执行,执行完毕后通过完成通道（completion channel）通知调度器，再触发下游依赖的 System 变为就绪状态。
>
> kmesh 提供 Mesh 资源的加载、序列化、打包、内存管理、异步流式加载。Mesh 资源包括顶点数据、索引数据、法线、UV 坐标等。
>
> ksprite 提供 Sprite 资源的加载、序列化、打包、内存管理、异步流式加载。Sprite 资源包括纹理、动画帧、碰撞体等。
>
> kmaterial 提供 Material 资源的加载、序列化、打包、内存管理、异步流式加载。Material 资源包括着色器、纹理、参数等。
>
> klight 提供 Light 资源的加载、序列化、打包、内存管理、异步流式加载。Light 资源包括点光源、聚光灯、环境光等。
>
> kinput 提供 Input 资源的加载、序列化、打包、内存管理、异步流式加载。Input 资源包括键盘映射、手柄映射、触屏映射等。
>
> kgltf 提供 GLTF 资源的加载、序列化、打包、内存管理、异步流式加载。GLTF 资源包括模型、材质、动画等。
>
> kpbr 提供 PBR 资源的加载、序列化、打包、内存管理、异步流式加载。PBR 资源包括金属度、粗糙度、环境贴图等。
>
> kapp App 生命周期和插件系统。App、Plugin、Schedule 阶段
>
> kutils — 通用工具集
>
> kasset — 资源加载与追踪（AssetServer、Handle<T>）。异步加载各种资源
>
> kcamera — 相机与可见性管理（View、culling）
>
> kshader — Shader 加载与处理（依赖 naga）
>
> krender — 核心渲染抽象（RenderApp、RenderGraph、提取/准备/队列的渲染阶段）。
>
> kwinit — 基于 winit 的窗口后端实现（WinitPlugin），负责事件循环]()
